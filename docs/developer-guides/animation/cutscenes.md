# Cutscenes

This guide describes the cutscene timeline: how to author a cutscene, how to preview it in the editor, how to play it, and how to drive it through MCP.

## Parts

| Part | Project | Responsibility |
|---|---|---|
| `CutsceneAsset` | `XREngine.Runtime.CutsceneIntegration` | Holds the tracks, the clips, and the bindings. It holds no runtime state. |
| `CutsceneCompiler` | `XREngine.Runtime.CutsceneIntegration` | Validates an asset and builds the time index. |
| `CutscenePlayer` | `XREngine.Runtime.CutsceneIntegration` | Holds the transport and evaluates the tracks. Each evaluation uses only the time. |
| `CutsceneDirectorComponent` | `XREngine.Runtime.CutsceneIntegration` | Opens an asset in a world and ticks the player. |
| `CutscenePreviewHost` | `XREngine.Editor` | Plays an asset in edit mode and restores the scene. |
| `CutscenePreviewSession` | `XREngine.Editor` | Owns the one cutscene that the panel and the MCP tools control. |
| `CutsceneResidencySession` | `XREngine.Runtime.CutsceneIntegration` | Connects the residency planner and its backend to a player for one open cutscene. |
| `CutsceneBakeTool` | `XREngine.Editor` | Bakes the residency manifest of an asset with the real player. |

## Animation Clip Tracks

An `AnimationClipTrack` plays `AnimationClipTrackClip` entries on its bound node. `CutsceneClipInstancer` makes one copy of each clip for each binding when the cutscene opens. The frame path makes no copies. A runtime slot must have its node before the open: call `CutsceneDirectorComponent.SetRuntimeSlot`. The value stays across a close and a later open, until a call with null clears it or the director is destroyed. If the slot has no node at the open, or gets another node later, the track writes nothing and adds a diagnostic.

Each frame runs in this order: store write, humanoid solve, root placement, and one IK solve. A VRIK target keeps its own scheduled solve.

- **Weights:** a total of zero leaves the original value. A total above one normalizes. A total below one blends from the original value. For a humanoid, the original value of a muscle is its live raw value at the first write, and the original value of an IK goal weight is its live weight. A target that has bones away from the bind pose and no readable muscle values fades from the neutral muscle pose. The first write adds a diagnostic for it.
- **Root placement:** a humanoid root is the start transform, then `RootOffsetPosition` and `RootOffsetRotation`, then the clip motion of this frame. The result is absolute, so repeated seeks do not drift. A target without a `HumanoidComponent` has no root placement. A root offset on such a target adds a diagnostic.
- **Lease:** while a clip has weight, the lease sets `EvaluationSuspended` on a sibling `AnimStateMachineComponent` and `AnimationClipComponent`. This flag is separate from `SuspendedByClip`. The lease puts back the earlier flag at clip exit and at stop. Playback time and the play and pause state of those components do not change.
- **No clip:** a target that has no clip with weight returns to its original values. For a humanoid, this includes each transform under the node and each member that the clips write.
- **Finish behavior:** a `KeepState` stop keeps the pose, and the next run records it as the new original value. If two tracks share a binding, the slot is restored if any of the tracks has `RestoreState`. This includes the root transform, the bone and muscle pose, and the clip members.
- **Pose preview:** if `HumanoidComponent.PosePreviewMode` is not `AnimatedPose`, the preview mode owns the pose. The track writes nothing and adds one diagnostic.

These features are not available from a sampled store. The open adds a diagnostic for each case:

| Case | Result |
|---|---|
| Additive clip | Plays as an absolute pose, without its reference pose. |
| Flip settings on a sibling `AnimationClipComponent` | The clips do not use them. |
| A track that calls code at the sample time | The member is not sampled. |

## Property Tracks

A `PropertyTrack` animates one member of a component on its bound node. Set these values:

- `ComponentType`: the short or full type name of the component. An empty value selects the scene node itself.
- `MemberPath`: the property or field to animate. Separate nested members with a period, for example `Parameters.VerticalFieldOfView`. Each member before the last must hold an object of a reference type.

The member must be a `float`, `Vector3`, or `Quaternion`. Each `PropertyTrackClip` has a `FloatCurve`, a `Vector3Curve`, and a `QuaternionCurve`. The type of the member selects the curve, and the other curves have no effect.

- **Binding:** the track finds the member at the first frame with weight, and again when the node of the slot changes. Each time a clip becomes active, the track walks the member path again. If an object on the path was replaced, the track writes the new object and adds one diagnostic. A replacement while a clip stays active is not seen until the next clip becomes active. A missing component, a missing member, or an unsupported type adds one diagnostic, and the track writes nothing. The write uses the typed setter of an `AnimationMember`, so a frame does not box the value.
- **Weights:** the rules of the transform track apply. A total of zero leaves the original value. A total above one normalizes. A total below one blends from the original value. Rotations blend as a normalized sum in one hemisphere.
- **Shared member:** tracks with the same slot, `ComponentType`, and `MemberPath` blend by weight and share one original value. The member is restored if any of the tracks has `RestoreState`.
- **No clip and stop:** a member with no clip with weight gets its original value back. A stop restores or keeps the value by the finish behavior, through `CutsceneStateSnapshot`.

## Audio Tracks

An `AudioTrack` plays `AudioTrackClip` entries through the `AudioSourceComponent` on its bound node. Set these values on a clip:

- `SourcePath`: the Ogg Vorbis (`.ogg`) or WAV (`.wav`) file to stream. A relative path starts at the folder of the cutscene asset file.
- `Volume`: multiplies the gain of the component and the blend weight of the clip.
- `ClipOffset`: skips the start of the file. `Speed` must be 1, and `Extrapolation` must not be `Loop`. A clip with another value adds one diagnostic and plays nothing.

The track streams the active clip with an `IStreamingAudioDecoder` (`VorbisStreamingDecoder` or `WavStreamingDecoder`), and it feeds the sources through `AudioSourceComponent.EnqueueStreamingBuffer`. The track keeps its own list of the sources and rebuilds it only when the listeners change, so a refill does not allocate. Each buffer holds 2048 frames, and the track keeps 4 buffers in the queue. The track also keeps the last 6 buffers of decoded frames, so a restart near the current position (a resume, a return to rate 1, or a new listener) does not seek the decoder backward. While a clip plays, the track sets `ExternalBufferManagement` on the component and turns off `AutoPlayOnQueue` on its sources. A stop or the end of the clip puts back these values and the source gain.

| State | Result |
|---|---|
| Forward playback at rate 1 | The sources play the clip from the cutscene time. |
| Jump seek to a new time during playback | Every active source stops, the decoder seeks, and the sources play again from the new time. A clip with an audio proxy plays the proxy at once and changes to the full decoder later (see [Tier Change](#tier-change)). |
| Pause, scrub (with or without `BeginScrub`), stop, or any rate other than 1 | The sources stop streaming. With no proxy, their gain is zero. With a proxy, a move of the playhead plays a scrub grain (see [Scrub Grains](#scrub-grains)). Playback at rate 1 starts again from the current time. |
| A listener comes into range | All sources of the track restart together, so they stay aligned. |
| A source runs out of buffers, for example after a long frame | The sources restart at the cutscene time, so the sound stays aligned with the picture. Until the restart, the clock does not read the old position. |
| No clip, or a time after the clip duration | The sources stop. A `Hold` clip has no sound after its duration. |

`Pause`, `BeginScrub`, and `SetRate` with a rate other than one stop the sources in the call itself, because a host can skip the ticks of a player that does not play. The edit-mode preview does this.

An audio track plays one clip at a time. An overlapping clip on the same track adds one diagnostic. A missing component and a file that does not open add one diagnostic each.

### Audio Proxies

The manifest bake makes one `AudioProxyAsset` for each audio clip source file, so that the player can play sound in the same frame after a far jump, before the full decoder reaches the new position (see [Tier Change](#tier-change)).

- **Format:** standard IMA ADPCM, mono, 22050 Hz (`ImaAdpcmDecoder.ProxySampleRate`), 4 bits for each sample. It uses the 89-entry step table and the 16-entry index table. Each block starts with a 4 byte header: the first sample (a little-endian 16 bit value), the step index, and one reserved byte. Then each byte holds two codes, the earlier sample in the low nibble. A block holds 1017 samples in 512 bytes (`AudioProxyAsset.DefaultBlockSamples`, the standard block of mono 22050 Hz IMA ADPCM WAV files). That is 11,101 bytes for each second.
- **Seek:** each header stores the full decoder state, so `ImaAdpcmDecoder` decodes only the block of the new frame. A random-access read gives exactly the same samples as a sequential read. `Read` allocates nothing.
- **Encode:** `ImaAdpcmEncoder.Encode(mono, blockSamples)` rounds each sample to 16 bits and tracks the decoder state, so the error does not grow along a block. The step index continues from the block before; the first block starts with the step that is nearest to the first difference. A 440 Hz sine at half scale decodes with a maximum error of about 0.0095 and an RMS error of about 0.0037.
- **Source conversion:** `AudioProxyBuilder` reads any `IStreamingAudioDecoder` and mixes the channels to their mean. When the source rate is above 22050 Hz, a low-pass FIR filter runs first: a Hamming-windowed sinc with its cutoff at 0.45 times the target rate (about 9.9 kHz), with `16 * ceil(sourceRate / 22050)` taps on each side (65 taps for 44.1 kHz), scaled to a DC gain of one. Without the filter, a 44.1 kHz source would be a plain 2:1 decimation, and all content from 11 to 22 kHz (sibilance, cymbals) would fold back below 11 kHz. The filter is centered, so it adds no delay; it holds the first and the last sample at the ends. Then a linear resampler computes output frame `i` at source position `i * sourceRate / 22050` with integers, so the result is deterministic and does not drift. The builder keeps the mono result in memory until the encode, so it runs at a bake and not in a frame.
- **Data:** `AudioProxyAsset` stores `EncodedData`, `SampleRate`, `BlockSamples`, `FrameCount`, `SourceReference`, and `SourceContentHash` (the XxHash64 of the source file). YAML stores `EncodedData` as one base64 value. `CreateDecoder()` opens a decoder that reads the stored bytes without a copy.
- **Source reference:** the portable reference of the source file (`game://` or `engine://`). The bake finds the file with `AudioTrackEvaluator.ResolveSourcePath`, the same rule that playback uses. A file outside the asset folders keeps its relative `SourcePath` (relative to the cutscene asset). A proxy never stores a full local path, so a source with a full path outside the asset folders gets no proxy and one diagnostic.
- **Storage:** the bake gives the proxies to the caller, which stores them in `CutsceneAsset.AudioProxies` (embedded in the cutscene asset). Clips with the same source share one proxy. A later bake uses a stored proxy again when its source reference, its source hash, its sample rate, its block size, and its data length all match, and encodes the source again otherwise. A source that does not open gives one diagnostic. The proxies are not part of `CutsceneManifestHash`.
- **Manifest:** the bake lists each proxy as an `Audio` asset with the key `CutsceneResidencyAssetKeys.ForAudioSource(proxy.SourceReference)` and no bucket entries. Its T0 size is the length of `EncodedData`. The residency session sends these assets to `AudioResidencyBackend` (see [Residency In Playback](#residency-in-playback)).
- **Shared rules:** `CutsceneAudioProxySources` holds the rules that the bake and playback share: `TryGetSourceReference` (the reference above), `HashSourceFile` (the XxHash64 of the file), and `FindProxy` (the proxy of a reference, case is ignored).

### Tier Change

A clip whose source has a proxy in `CutsceneAsset.AudioProxies` uses two tiers. A clip with no proxy plays as before: a jump seeks the full decoder on the update thread, and a cutscene with no proxies plays exactly as before.

1. A restart outside the ring of decoded frames (a jump, or the first play at a time after zero) does not seek on the update thread. In the same frame, the track fills the queue from the proxy (T0) at the exact frame.
2. An `AudioDecoderSeekWorker` seeks the full decoder on a background task to a buffer start after the queue. The lead is at least 4 buffers (8192 frames, the queue of the restart). The first refill comes about one buffer after the restart, so a longer seek adds buffers for twice the estimated seek time beyond that buffer. The estimate is the larger of the measured time of the last seek of the decoder and, for an Ogg Vorbis decoder, 2 ms for each second of the target time (a backward Vorbis seek decodes from the start of the file). A cold Vorbis seek to 120 s therefore asks for 15 buffers. The update thread does not use the decoder while the worker has work. A newer jump cancels a seek that did not start, and makes the result of a running seek stale; the task then seeks to the newest frame. A seek that ends after its buffer passed asks again at a later buffer with twice the lead (at most 256 buffers).
3. At the first buffer boundary at which the full decoder is at the produced frame, `AudioTierCrossfader` crossfades from the proxy to the full decoder over 20 ms with equal (linear) gain: the full gain is `t = (k + 0.5) / n` and the proxy gain is `1 - t` for frame `k` of `n`. The sum of the gains is one.
4. The crossfader resamples the proxy (22050 Hz mono) to the rate and the channel count of the full decoder: full frame `f` is at proxy position `f * 22050 / fullRate` (integer math, linear interpolation), and each channel gets the same value. The bake puts proxy frame `i` at source position `i * sourceRate / 22050` with no filter delay, so the two signals are sample-aligned.

The queue keeps one format and one frame rate across the change, so the frame count of the audio clock does not change and the clock does not jump. The ring holds the frames that played, so a restart inside the ring (a resume) plays the same frames again. The two signals are coherent and sample-aligned, so equal gain keeps the level flat through the fade, with no step. (Equal power would be up to 3 dB louder in the middle of the fade and could clip.) If the background seek fails, the clip plays the proxy to its end and adds one diagnostic.

**Stale proxy:** when the track is created, the evaluator compares `SourceContentHash` of each proxy with the hash of its source file, one time. A file with the same length and write time uses a stored hash, so a preview recompile does not read it again. This is a heuristic: a file replaced with the same length and write time keeps the old hash. The cache holds at most 256 files and ignores case only on Windows and macOS. The first open reads each proxied source file in full on the creating thread. A proxy that does not match, or whose file cannot be read, adds one diagnostic and never plays. After a jump, that clip is silent until the full decoder is ready, and then fades in over 20 ms. A proxy whose data does not open gives the same result with its own diagnostic.

### Scrub Grains

While the transport does not stream (a pause, a scrub, a stop, or a rate other than 1) and the playhead moves, a track with a proxy plays one grain from the proxy at the playhead (`AudioScrubGrainPlayer`). A grain is 60 ms long, at the rate and the channel count of the full decoder, with a squared-sine fade of 10 ms at each end, so its first and last frames are zero. A move during a grain waits for the end of that grain, and then the newest position plays. A playhead that does not move plays nothing more. The grain buffers are allocated when the clip opens, so a grain does not allocate. Reverse playback at a rate of 2 or faster (`AudioTrackEvaluator.SilentReverseRate`) plays no grains; slower reverse playback does. A jump seek (for example a skip or a move to the start while paused) and a gate hold play no grains. A clip with no proxy, or with a stale proxy, is silent.

### Audio Clock

A cutscene with an audio track that has `DrivesClock` set (the default) starts its clock in `AudioDisciplined` mode. In each play step, after the clock advances and before the evaluation and the event dispatch, the player reads the heard position from the first such track of the last evaluation. The track reads the playback clock of its first source through `IAudioTransport.TryGetPlaybackClock`. The heard position is the frame count before the queue, plus the source position, minus the output latency. While that value is below the frame of the last restart, the listener does not hear the new queue yet (for example during the 300 ms NAudio output latency). The clock then stays on wall time with no correction, and this is not a loss of the clock: no diagnostic and no fallback. The same applies when the sources wait for a restart because their queues differ. A warm-up has a bound: if it lasts longer than the output latency plus 250 ms (and at least 500 ms) of play steps after the restart, the device does not reach the queue, and the player treats it as a lost clock, with the fallback and its one diagnostic below. The first valid heard position after a restart (a start, a seek, a resume, a return to rate 1, or a new listener) moves the clock to that position in one step, if the difference is 100 ms or less. During the warm-up the clock runs on wall time, so it is ahead of the sound by about the output latency. The step removes this offset at once. It is not a hard resync: it raises no `Discontinuity`, and the high-water mark below keeps a backward step from firing an event again. After that step, the clock moves toward the heard position by at most 5 percent of the frame step. When the difference is more than 100 ms, the clock jumps (a hard resync): the player raises `Discontinuity` with `Jump` intent and `ClockResync` kind (or `Full` kind if the camera also changed in that tick), and the events across the jump follow the seek policy of each track.

A restart runs in the tick: it seeks the decoder and decodes the new queue into the ring while the sources still play, then stops the sources, queues the decoded buffers, and plays. The sources are stopped only while the queue is copied and played, so a mixer update in that window (one OpenAL Soft period, about 20 ms) is less likely than one between a stop and a long decode. A batch play call (`alSourcePlayv`) does not help here, because a track has one source for each listener, and each listener has its own transport context. The sources start only at its end, so the player removes from the clock advance of the next tick the time that delayed the clock track: the restarts in service order up to and including the restart of the clock track. A restart of another track while the clock track plays on removes nothing. If no track drives the clock, nothing is removed. A long decoder seek therefore makes one long frame, but no hard resync. The removed time is wall time; it is not scaled by a time dilation. A track that becomes the clock track with no restart, for example when the clip of the earlier clock track ends, slews and does not step.

The clock reads the first source of the track, so only that source controls the clock reading and a restart of all sources. If the first source stops before the end of the data, all sources restart. The first such stop after a valid clock reading, for example after one long frame, does not count toward the warm-up bound. Later consecutive stops with no valid reading between them keep the warm-up time, so a first source that never plays reaches the bound and the fallback. Their restart time is not removed from the clock.

Another source that stops (for example, the source of a second listener) restarts alone, once. It starts at the buffer that the first source plays, so it can be up to one buffer (2048 frames) behind. It gets another restart only after it plays a buffer, or after a restart of all sources. This does not need a clock reading, so it also works on a track that does not drive the clock. A seek or a resume starts a new count of starves for the warm-up bound. If it stops again, the track adds one diagnostic for that listener and gives the source no sound until the next restart of all sources. The first source and the clock continue. After the sources play the last buffer of the clip and stop, the player does not read the heard position. The listener still hears the output latency there, so the value stays behind the clock.

Play dispatch keeps a high-water mark: a play step never fires an event at or below the highest position that playback reached. So a clock correction never fires an event twice. A seek, a hard resync, and a stop move the mark to the new position. Reverse playback followed by forward playback does not fire the crossed events again. A seek back does.

| Transport | Clock |
|---|---|
| OpenAL | `AL_SAMPLE_OFFSET_LATENCY_SOFT` from `AL_SOFT_source_latency`. Without the extension, there is no clock. |
| NAudio | The mixer position. The latency is the `DesiredLatency` of the `WaveOutEvent` output, which is an estimate. |
| WebAudio | No clock. |

If the transport has no clock, the player changes the clock to `Wall` mode, sets `CutscenePlayer.IsAudioClockFallback`, and adds one diagnostic. The clock goes back to `AudioDisciplined` when the transport reports a clock again, and also at a stop.

## Event Tracks

An `EventTrack` holds a list of `CutsceneEvent` entries. Each event has a `Time`, a `Key`, and a `Payload`. Events are the only side effect of a cutscene. They never change state that a seek or a scrub needs, so put that state on a sampled track.

Subscribe to `CutscenePlayer.EventFired` or `CutsceneDirectorComponent.EventFired`. The director subscription stays across a close and a later open. Each call gets a `CutsceneFiredEvent` with the track index, the event index, the event, and `FromSeek`.

| Movement | Result |
|---|---|
| Forward playback | Fires each crossed event once, in time order. An event at the end of a frame fires in that frame and not in the next one. After the open, a stop, or a backward move, an event at the start position also fires. |
| Reverse playback | Fires nothing. |
| Forward jump seek | Fires by `SeekPolicy`: `Skip` (default) fires nothing, `FireLatest` fires the last crossed event of each key, and `FireAll` fires all crossed events in time order. |
| Backward seek | Fires nothing. Forward playback fires the events again when it crosses them. |
| Scrub | Fires nothing, unless the track sets `FireDuringScrub`. Then a forward scrub step fires by `SeekPolicy`. |

The events of a tick fire after the evaluation, so a handler sees the state of the new position. A handler that throws adds one diagnostic for its track, and the other events still fire. A handler can call `Stop`, `Seek`, or `Play`. A stop or a seek ends the tick at once: the remaining events of the step do not fire, and `Finished` is not raised for that step. The state of the player is final before `Finished` is raised, so a `Finished` handler can stop or restart the player.

The editor preview sets `CutscenePlayer.IsPreview`. A preview fires only the tracks that set `FireInPreview`, so gameplay script does not run while an author moves the playhead. `CutscenePreviewHost.EventFired` gives those events to the editor. A recompile after an edit does not fire the events before the position again, and an event at the position that has not fired yet still fires. With a loop range, a play step stops at the loop edge, so events after the loop end do not fire.

An event track does not use its binding slot. The binding table does not check it.

### Completion

Put completion logic on `CutscenePlayer.Finished` or `CutsceneDirectorComponent.Finished`, not on an event at the end of a clip. The player raises `Finished` from its state: once when forward playback or a jump seek, for example a skip, reaches the end. A skip that jumps over the last events with `Skip` still raises it. A scrub and a stop do not raise it. A later move away from the end lets it be raised again.

## Simulation Control Tracks

A physics chain or a particle emitter keeps state from frame to frame, so its state is not a function of the time. A `SimulationControlTrack` tells what the simulations on its bound node do after a discontinuity. The track has no clips, and it applies for the full cutscene. It controls each `PhysicsChainComponent` and each `ParticleEmitterComponent` of the node. A discontinuity for the simulations is a jump seek, a scrub step, a camera cut, or a stop. A hard resync to the audio inside one shot is a small time correction: it resets only the temporal render history (see [Discontinuity Resets](#discontinuity-resets)), and the simulations continue. A resync and a cut in the same tick count as a cut.

| `Policy` | After a discontinuity |
|---|---|
| `SettleFromReset` (default) | The simulation resets to the current pose and then runs normally. |
| `WarmUp` | The simulation resets and then runs fixed steps for `WarmUpSeconds` (default 1 s). The steps use at most `WarmUpBudgetMilliseconds` (default 2 ms) of wall time in each frame, and the rest continue in the next frames. |

`Seed` (default 0) is the random seed of a particle emitter at a reset or a warm-up, so each run gives the same particles. Each emitter of a node adds its index times 7919 to the seed, so two emitters on one node do not repeat the same random pattern.

| Target | Reset | Warm-up | Hold |
|---|---|---|---|
| `PhysicsChainComponent` | `ResetSimulationToCurrentPose()`. The chain applies the reset at the start of its next simulation step, after it reads the current pose of its bones, and the reset replaces that step. A GPU chain then dispatches one step with a zero time scale, so the GPU particles and the GPU bone palette show the reset pose in that frame. The cutscene tick writes no bone. A chain with weight zero or disabled by distance drops the request, because it resets itself when it updates again. | None. A chain with `WarmUp` settles from the reset, and the track adds one diagnostic. | A reset request in each held frame. |
| `ParticleEmitterComponent` | `Prewarm(0, Seed, 0)`: clears the particles and sets the seed. | `Prewarm(WarmUpSeconds, Seed, WarmUpBudgetMilliseconds)`. The emitter runs steps of `PrewarmStepSeconds` (1/60 s), at least one in each call, and continues the rest in its own update in place of the normal step. All steps use the emitter transform of the `Prewarm` call, so the result does not depend on how the budget splits the steps across frames. | `BeginSimulationHold` and `EndSimulationHold`. A held emitter does not step. The hold is separate from `IsSimulating`, `Pause`, and `Resume`, and it does not change the tick registration. |

The player applies the resets and the warm-ups at the end of `Tick`, never in `Seek` or `Stop`. A stop releases a hold at once (this changes no user state), and its reset waits for the next tick. One discontinuity gives one reset of each simulation, also when a cut and a jump occur in the same tick. If two tracks bind the same node, the first track controls each simulation, and the second track adds one diagnostic. A node with no simulation adds one diagnostic. The targets are found again only when the bound node of a track changes, so a component that you add to or remove from the same node during playback is not seen until then.

During a scrub, each step resets the simulations, and they hold the reset pose. A held emitter is cleared once, not at each step. The hold ends, and a `WarmUp` track starts its warm-up, when the player plays at a rate within 0.05 of one (`SimulationControlEvaluator.ResumeRateTolerance`), when `EndScrub` ends a scrub, or at a jump seek (also during `BeginScrub`, for example the jump of a preview recompile). A scrub with only `UpdateScrub` seeks and no `BeginScrub` holds until playback at a rate near one or a jump. A tick with no discontinuity and no hold does no simulation work and does not allocate.

The warm-up budget measures the CPU time that records the emitter steps. The GPU runs the compute work later, so the budget does not limit the GPU cost. The budget applies to each emitter, so N emitters on a node can use N times the budget in one frame.

## Discontinuity Resets

`CutsceneCameraRouter` owns a `CutsceneDiscontinuityHandler`. At each `Discontinuity`, after the router claimed the camera of the new shot, the handler resets the target viewport once. `CutsceneDiscontinuity.Kind` tells which resets run: `Full` for a seek, a camera cut, or a stop, and `ClockResync` for a hard resync to the audio with no camera change.

| Reset | Kinds | Effect in the Default, Advanced, and RVC pipelines |
|---|---|---|
| `XRViewport.InvalidateTemporalHistory(publishNotifications: false)` | `Full`, `ClockResync` | Advances `XRCamera.TemporalHistoryEpoch`. The camera loses its previous view-projection (camera motion vectors), and the frame view history marks the view as having no valid history. TAA and TSR history then reset. Spatial hash AO, the only temporal AO pass, follows that history for mono views. |
| `XRCamera.ResetAutoExposureHistory()` | `Full` | Auto exposure does not read the epoch, and it blends from the exposure of the previous frame. The reset makes the next update set the metered exposure in one step, on the GPU path (OpenGL, Vulkan, and WebGPU) and on the CPU path. The reset records the new camera epoch. `VPRC_ExposureUpdate` passes the epoch that the view history ledger recorded at the capture of the rendered frame, so a frame from before the reset that still renders does not use it, and the first new frame uses it once. This guard applies only where the desktop view history ledger authors history. A frame with no ledger epoch (output sequence 0, view history authoring off, a stereo pass, or the front-buffer CPU path) counts as a new frame, so on those paths a frame from before the reset can still use it; the reset never stays blocked. On the CPU path, one snap request waits for its luminance result; if no result comes in 1 s (for example with no current renderer), a new request starts. |

The handler does not reset GI history (radiance cascades, ReSTIR reservoirs, surfels, and DDGI probes), the previous model matrix and skin palette of each mesh, the Advanced deformation history, or the RVC temporal cache. These have no reset hook for a view discontinuity. Without a target viewport, no render state resets.

## Residency

`CutsceneResidencyPlanner` decides which level of each asset must be resident, and by which time, around the playhead. The levels are T0 (proxy), T1 (coarse), and T2 (target). The planner sends requests to an `IResidencyBackend` and does no IO itself. The director and the editor preview run it through a `CutsceneResidencySession` (see [Residency In Playback](#residency-in-playback)). `TextureResidencyBackend` is the texture backend and `AudioResidencyBackend` is the audio backend; no mesh backend exists yet.

- **Input:** a `CutsceneResidencyManifest` holds a shared asset table, the kind of each asset (`EResidencyAssetKind`: `Texture`, `Mesh`, or `Audio`), and `ResidencyBucket` entries in time order, with no overlap. Each `ResidencyEntry` gives an asset index, a target level, and a screen coverage. A bucket can mark a camera cut at its start. The kind is per asset and not per entry, because one asset has one kind. The manifest is serializable: the properties have setters, and the planner constructor calls `Validate`. `SelectKind(kind)` makes a manifest of one kind.
- **Compression:** the buckets are delta-compressed. A key bucket (`IsDelta` false, the default) lists all of its entries. A delta bucket (`ResidencyBucket.CreateDelta`) lists only the entries that are new or changed against the bucket before, and the asset indices in `Removed`. The first bucket and each bucket at a camera cut must be key buckets. `CutsceneResidencyManifestBuilder` rounds each coverage to 1/128, merges adjacent buckets with equal entries (not across a cut), and writes a key bucket at each cut, at least every 4 seconds (`DefaultKeyInterval`), and where a delta is not smaller than the full list. `CutsceneResidencyBucketCursor` decodes any bucket: a move starts at the key at or before the bucket, or continues from the current bucket, and allocates nothing after its constructor. The planner reads its window and the hold targets through one cursor. A synthetic 10-minute bake with 300 assets stores 23,400 entries instead of 240,000, in 720 buckets instead of 2400.
- **Calls:** call `Open` one time. It requests T0 for each asset. Then call `Update(position, rate, seek, deltaSeconds)` one time in each frame on the update thread. `seek` is null when no seek occurred. A backend reports complete work with `NotifyCompleted`, from any thread. The next update applies it and raises `LoadCompleted`.
- **Plan:** an update plans again only when the playhead goes into another bucket, the window covers other buckets, the rate changes, a seek occurs, the dwell gate changes, or a load completes. Otherwise it allocates nothing and sends nothing. The window is 5 seconds ahead at rate 1, scaled by the absolute rate, in the direction of travel, plus 0.5 seconds behind. At rate 0 (a pause), the window is the forward window of rate 1, so a pause does not cancel the prefetch. The planner requests one level above the resident level at a time. Requests sort by level, then by the time until the playhead needs them, then by screen coverage in descending order. A bucket behind the playhead sorts after the buckets ahead of it. Running work of the current generation stays while the window needs its level or a higher one, so a load that completes during an update is not cancelled. A jump, an asset that leaves the window, and a closed dwell gate cancel the running work.
- **Jump:** a `Jump` increments `Generation` and cancels the work of older generations. A late result of an older generation runs no callback.
- **Scrub:** a `Scrub` sends nothing above T0 until the playhead stays within 50 ms of timeline time for 120 ms of wall time. A new drag cancels the T1 and T2 work that did not complete. A `Jump` does not use this gate.
- **Eviction:** `Evict(maxCount)` releases T1 and T2 data. First it releases the assets outside the request window, farthest from the playhead first. Then it releases the assets in the window, farthest deadline first. It never releases T0. `Evict(maxCount, outsideWindowOnly: true)` releases only the assets outside the window. `CutsceneResidencySession` calls that form under memory pressure (see [Residency In Playback](#residency-in-playback)). An eviction allocates nothing.
- **Backend contract:** `IResidencyBackend.Cancel` on a complete ticket releases the data that the ticket holds. Set the level that `GetLevel` reports before the call to `NotifyCompleted`. A level that only a cache supplies, with no ticket, is not held.
- **Playback wait:** `PlaybackWaitEnabled` is off by default. When it is on, forward play that crosses a camera cut sets `IsHoldingPlayback` until the next shot has its target levels or `PlaybackWaitMaximumSeconds` (default 1 second) passes. The caller holds the clock at `PlaybackHoldTime`. A jump, a scrub, and reverse play never hold, and they end a hold. A pause keeps a hold, and the paused time does not count toward the maximum wait. `PlaybackWaitTimeoutCount` counts the waits that reached the maximum.
- **Close:** `Close` cancels all work and releases all levels, T0 included. After it, a completion runs no callback and `Update` does nothing.
- **Textures:** `TextureResidencyBackend` sends the levels to the imported texture streaming manager as explicit residency requests (see [Texture Streaming](../../architecture/rendering/texture-streaming.md#explicit-residency-requests)). T0 is the texture preview, T1 is the first mip with a largest side of at most `CoarseMaxDimension` (default 512), and T2 is the full source size. The texture quality setting and the VRAM budget can lower T2. A request is not visibility and does not pin the texture. A cancel of a complete ticket releases the hold, and the texture returns to visibility-driven residency. `GetLevel` reports the highest level of a ticket whose mip is resident now.
  - Create it with an `AssetManager` or with a `Func<Guid, XRTexture2D?>`. The `AssetManager` form finds a texture by a runtime ID in the loaded assets and then in the object cache (`XRObjectBase.ObjectsCache`), because a texture that a model import creates is a live object but not an asset of the manager. Then it finds the textures of a stable key (see [Asset Keys](#asset-keys)) through an index of the live textures. A texture that is destroyed or queued for destroy is not found. The index scans the object cache at its first miss and keeps the key of each texture that it saw. It scans again only after `BeginSelection`, so a manifest selection scans at most one time, also when many keys miss (see the next items for the two other cases). The backend resolves each asset one time for each selection and uses the same textures for `CanResolve` and `Request`. It works on textures that are already loaded. It does not load assets.
  - One key can have more than one live texture, for example the eager and the deferred texture of one import. A request then goes to each of them, and `GetLevel` reports a level only when it is resident for each of them. The order is the runtime-ID order of one index build; it can change at the next start, which does not matter, because every texture gets the request. A texture that streaming does not accept is left out of the request; `PartialRejectedTextureCount` counts it, and the first one of each asset gives one warning.
  - Within one selection, a kept result with a destroyed texture (for example after a reimport while a preview is open) is resolved again, and the first such result lets the index build one more time. At a selection, the index also builds again when the object count changed since its last build, so a new duplicate of a key that hits is found.
  - `CanResolve(assetId)` is true when the asset is a live texture now. `AreAssetsLoading` is true while model imports are active (`AreModelImportsActive` gives the same value for the shared manager). `IsUnderMemoryPressure` is true while the last streaming evaluation found VRAM budget pressure (`ImportedTextureStreamingManager.IsUnderBudgetPressure`): the budget fit gave a texture less than its desired size, the streamed textures used more than the available budget, or the Vulkan allocator budget stopped promotions. The per-frame limits of a budget profile are not memory pressure, because they limit the work of a frame. A release would add demotion transitions to that work.
  - Call `AttachPlanner(planner)` before `planner.Open()`, so that the backend can report complete work. Call `SetPlayhead(position, rate)` before each `planner.Update`, so that request deadlines become frame deadlines (`EstimatedFramesPerSecond`, default 60). Without a playhead, requests have no deadline.
  - By default it holds the `Cutscene` texture streaming budget profile. The profile is global to the streaming manager, so the backends of one manager share it with a reference count: the first backend selects `Cutscene`, and the last `Dispose` selects `Default` again. Two open directors therefore keep the profile until both close. The `Cutscene` limits are provisional engine settings.
  - The backend rejects a request when the asset is not a loaded texture, when streaming does not track the texture, or when the source size for T1 is not known yet. It logs a warning and counts the rejection in `RejectedRequestCount`.
- **Audio:** `AudioResidencyBackend` handles the audio clip sources that have a proxy, by the key `CutsceneResidencyAssetKeys.ForAudioSource`. T0 is the proxy; it is part of the cutscene asset, so it is resident at once. A stale proxy never plays, so the backend rejects T0 for it with no log (the track gives the one diagnostic); T1 and T2 of its source still load. T1 and T2 open the full decoder of the source file on a background task and seek it near the deadline: the file frame of the clip that plays at the deadline, or the first frame of the next clip. The ticket holds the open decoder until the planner cancels it, so the file data is in the cache of the operating system before the playhead gets there. The track opens its own decoder for playback. The backend sets the level before `NotifyCompleted`. A cancel of a complete ticket closes its decoder, and a cancel of running work makes the task close its decoder at its end and report nothing. `BuildManifest()` makes the manifest of the audio planner from the timeline: one asset for each source, buckets at the clip edges, and T2 with the coverage 1 for each clip range, because sound has no screen coverage. A request for an unknown asset is rejected and counted in `RejectedRequestCount`; a failed open or seek is logged and counted in `FailedLoadCount`.

### Residency In Playback

`CutsceneDirectorComponent` and `CutscenePreviewHost` each own one `CutsceneResidencySession` while a cutscene is open:

- **Open:** `CutsceneResidencySession.TryOpen` creates the backend, selects the manifest, and opens the session. A current, valid baked manifest is used as it is. A missing, stale, or invalid manifest (`ECutsceneManifestState.Invalid` also covers a hash that could not be computed) gives the approximate manifest and one diagnostic. The selection also calls `IResidencyBackend.BeginSelection` and resolves each texture of the manifest one time (`CanResolve`, true by default). If more than `CutsceneManifestMatch.MaxUnresolvedTextureFraction` (10%) of the textures of a current baked manifest are not found, the content hash is still current, but the manifest does not match the scene: the state is `ECutsceneManifestState.Unmatched`, and the session uses the approximate manifest with one diagnostic. For a small manifest one missing texture can be enough (1 of 9). While `IResidencyBackend.AreAssetsLoading` is true, a missing texture can still load, so the session keeps the baked manifest (`IsWaitingForAssets`) and selects again one time at the first update after the loading ends. The new selection replaces the planner, so it waits while the planner holds playback at a cut. After `AttachPlayer` with another player (a preview recompile), the stored compile and bindings are old, so the selection waits for the next `Refresh` of the host. Textures that are not found at or below the fraction are not sent to the backend; one diagnostic gives their count, and `UnresolvedTextureCount` holds it. A manifest diagnostic is added again only when its reason changes, for example a key mismatch and then an edit, not when a refresh gives the same reason. A residency failure (no backend, or an exception from the factory, the selection, or the open) gives one diagnostic, disposes the backend, removes the gate, and the cutscene opens and plays without residency. Mesh assets have no backend, so they give one more diagnostic, and they stay at the residency that visibility selects. The session sends only the texture assets to the texture backend. Audio assets go to an audio backend with its own planner, `CutsceneResidencySession.AudioPlanner`: `Create` and `TryOpen` take an optional factory, and the default (`CreateDefaultAudioBackend`) makes an `AudioResidencyBackend` for a cutscene with audio proxies. The audio planner gets each playhead update, opens and closes with the session, and is made again at a `Refresh` only when the audio inputs changed (the audio clips, the proxies, or the audio assets of the manifest), so a refresh after a model import keeps the open decoders. A refresh makes the new audio part before it changes anything, so a throw leaves the session as it was. It never holds playback, and memory pressure does not release its data. If the manifest has audio assets and no audio planner exists, one diagnostic gives their count and the cause: no backend was made (no proxies, or the factory gave none), or no proxy matches an audio clip. The constructor calls `backend.AttachPlanner(planner)`, and `Open(player)` calls `planner.Open()` and sets the session as `player.PlaybackGate`.
- **Frame:** the host calls `BeginTick`, then `player.Tick`, then `CompleteTick`. A play step updates the planner through the gate, before the player evaluates. Any other tick updates it in `CompleteTick` with `player.LastTickSeek`: the intent of a resolved seek, or `Jump` for a `Stop` since the last tick. The player passes the same value to the gate, so `Stop(); Play();` before a tick is a `Jump` too. A hard audio resync is a correction of normal play, so the planner sees it as a play step. A paused or scrubbing player reports rate zero. Each update calls `backend.SetPlayhead(position, rate)` first. A paused preview that does not tick the player calls `UpdateIdle`, so the dwell gate of a scrub can open. A preview loop wrap is a jump seek, so the planner sees it as a `Jump`.
- **Preview recompile:** an edit recompiles the preview. The session, the backend, and the budget profile stay, and `AttachPlayer` moves the gate to the new player at once. The manifest selection (hash, approximate manifest) and the planner swap (`Refresh`) wait until no edit came for `CutscenePreviewHost.ResidencyRefreshDelaySeconds` (0.25 s), so a clip drag does not repeat that work in each frame. A refresh adds a manifest diagnostic only when the manifest state changes.
- **Memory pressure:** after each planner update, the session reads `IResidencyBackend.IsUnderMemoryPressure` (false by default). Under pressure, it calls `Evict(PressureEvictionsPerUpdate, outsideWindowOnly: true)` at most one time for each new budget evaluation (`IResidencyBackend.MemoryPressureFrameId`): at most 4 assets release their T1 and T2 data, outside the request window first and farthest from the playhead first. A release demotes only after the demotion cooldown, so the flag can stay set for some evaluations. A flag whose evaluation does not advance, for example when no viewport collects, is stale and releases nothing. T0 data stays. Data in the window also stays, because the streaming budget fit already lowers those textures, and the next plan would request their levels again. `PressureEvictionCount` counts the releases. With no pressure, the check allocates nothing.
- **Close:** the director closes the session at `Close`, at component deactivation, at `OnEndPlay` (world or scene end), and at destroy. The session closes the planner and then disposes the backend. Then the player restores the targets.
- **Backend:** the director uses `ResidencyBackendFactory`, or the static `CutsceneDirectorComponent.DefaultResidencyBackendFactory`. The editor registers the default in `CutscenePreviewSession.Initialize` as `new TextureResidencyBackend(Engine.Assets)`, and the preview session gives the same factory to each preview host. The windowed desktop composition (`RuntimeRenderingBootstrap`, with asset services) registers the same factory through `CutsceneResidencyRegistration.InstallDefaultBackendFactory`, so a game executable also gets texture residency. A headless host calls `CutsceneResidencyRegistration.InstallUnavailable`, so a director with no factory opens without residency and without the per-open diagnostic. If `ResidencyEnabled` is true (the default) and no factory gives a backend, the director opens without residency and adds a diagnostic. A `CutscenePreviewHost` created without a factory runs without residency.
- **Playback wait:** `PlaybackWaitEnabled` and `PlaybackWaitMaximumSeconds` on the director and on the preview host set the planner values. Both are off by default; the panel option is **Wait At Cuts**. When forward play crosses a camera cut whose shot is not resident, the gate limits the step to the last flick before the cut, so the frame never shows the new shot. The player stops the audio sources at once and keeps them stopped while `player.IsHeldByGate` is true. The hold ends when the targets are resident or the maximum wait passes; the sources start again in the same tick as the release. An event at the cut fires only after the release.

### Manifest Bake

`CutsceneBakeTool.Bake(asset, options)` runs the compiled timeline with the real `CutscenePlayer` and a `Manual` clock. It samples 4 times each second and at the start of each camera cut clip. For each sample, it updates the world matrices, finds the assets of each shown node with an `ICutsceneResidencyAssetCollector`, and computes the screen coverage of the bounding sphere in the view of the active camera (`CutsceneResidencyView`). A sphere behind the near plane covers nothing, so the camera orientation counts. An asset needs T2 at or above `TargetCoverage` (default 0.1) and T1 below it. Each sample gives one bucket that ends at the next sample, and a bucket that starts at a camera cut has the cut flag. Because the bake uses the real evaluator, the result includes the animated poses, the clip starts and offsets, and the spawned objects. The bake restores every recorded value at the end and destroys the spawned instances.

- **Inputs:** `CutsceneBakeOptions` takes the binding resolver, the runtime slots, the scene roots (so that objects that no track binds are also seen), the collector (default `CutsceneRenderableAssetCollector`, which reads the sub-meshes and the 2D textures of `ModelComponent` LOD materials; it skips a texture with no file, such as a generated material default, because streaming cannot load it), and the audio decoder factory.
- <a id="asset-keys"></a>**Asset keys:** a model import makes new runtime IDs for its textures and sub-meshes at each import, and the model has no stored ID. So the default collector records stable keys from `CutsceneResidencyAssetKeys`, not runtime IDs. A texture that is its own stored asset (its file has the asset extension) uses its persisted ID. A texture with a source file (`OriginalPath`, which a model import sets) uses a name-based GUID of the portable source reference (`game://` or `engine://`, from `AssetSerializationServices.Current.TryCreatePortableAssetReference`) and the sampler name, which is the cache identity of the importer. A path that is already portable is used as it is. The reference has `/` separators and upper case on every OS. A texture with no source path that is embedded in a stored asset uses its stored ID. Any other texture uses a key of its own file reference and sampler name. A sub-mesh uses a key of its place in the scene: the persisted ID of the scene that owns the root node, the node path from the root (each node name with its index among the siblings, or the scene roots, of the same name), the component index, and the sub-mesh index. The keys stay the same after a new import of the same model, on another machine, and in another project folder. A file outside the game and engine asset folders has no portable reference, so its key uses the full path; the bake reports the count of such keys in one diagnostic. A custom collector can use any ID that `IResidencyBackend` can resolve.
- **Cooked builds:** the cook (`ProjectBuilder`, through `CookedSourcePathPolicy.MakeSourcePathsPortable`) writes the `OriginalPath` of each cooked asset and its embedded assets as a portable reference when the path is in an asset folder (see [Portable Source Paths](../../architecture/assets/cooked-asset-aot-and-io.md#portable-source-paths)). A cooked build therefore computes the same texture keys as the editor, although it runs from another folder.
- **T0 budget:** the T0 size of a texture is a 64 px uncompressed preview with mips (about 21 KB). The T0 size of a sub-mesh is 74 bytes for each vertex of its lowest LOD. The T0 size of an audio proxy is the length of its encoded data (see [Audio Proxies](#audio-proxies)). The bake returns a `CutsceneT0Report`. If the total is above `T0BudgetBytes` (default 64 MiB), the bake throws `CutsceneBakeException`, whose message lists the largest assets. The bake does not remove assets to fit.
- **Store:** the bake does not change the asset. Set `asset.Manifest` to the result, `asset.ManifestContentHash` to `CutsceneManifestHash.Compute(asset)`, and `asset.AudioProxies` to the proxies of `Bake(asset, options, out report, out audioProxies)`. The panel **Bake Manifest** button does this.
- **Stale manifest:** `CutsceneManifestHash` hashes the duration, the restore setting, and the object graph of the bindings and the tracks: a stable type name (namespace and name, with no assembly name or version), then each public property with a public setter and no `YamlIgnore`, and each public field, in name order. A referenced asset, for example an animation clip, adds only its ID, so an edit inside that asset does not make the manifest stale. A .NET or engine upgrade does not change the hash; a rename or a move of a track or clip type does. A member value that the hash cannot read exactly (a dictionary, a delegate, a type object, or a value type with no settable member, such as `decimal`, `TimeSpan`, or `DateTime`) throws `NotSupportedException` with the member path, and playback reports an invalid manifest. A new member of such a type therefore cannot escape the stale check. It does not include the manifest, the hash, or the name. Any later change to the asset makes the manifest stale (`ECutsceneManifestState.Stale`), and playback then uses the approximate manifest for the whole timeline.
- **Approximate manifest:** `CutsceneApproximateManifest.Build` splits the timeline at each clip edge. A bucket holds the assets of the bound nodes, and their descendants, whose tracks have an active clip there. It uses the open poses and the camera of the active cut at its open pose. An asset at or above the target coverage, or with no camera, needs T2, and any other asset needs T1. It never drops an asset for its coverage, because the open pose can be wrong. It does not see objects that no track binds.
- **Cook:** `CutsceneCookCheck.GetRejection(asset, shippingCook: true)` gives the reason to reject an asset whose manifest is missing, stale, or invalid. A development cook accepts it. The project builder does not call this check yet; the call belongs in the cooked-content step of `ProjectBuilder` (`CookContent`) for each `CutsceneAsset`.

## Author A Cutscene

1. Open **Cutscene Sequencer** from the panel menu, next to **Animation Clip Editor**.
2. Select a scene node. Click **Add Director To Selected** if the node has no `CutsceneDirectorComponent`.
3. Click **Create Cutscene Asset**. The new asset has a length of 10 seconds.
4. Click **Start Preview**.
5. Select the node to animate, and click **Add Transform Track**. The track has one clip that covers the whole cutscene, with one key at the current transform. The node does not move yet.
6. Click the clip to select it. Move the playhead, move the bound node, and click **Add Key At Playhead**. The key always uses the transform of the node that is bound to the track. **Remove Key At Playhead** removes a key within half a frame of the playhead.
7. Select a node that has a `CameraComponent`, and click **Add Camera Track** to show that camera while the clip is active.
8. Click **Save Asset**. A new asset goes to the `Cutscenes` folder of the game assets.

Save the scene after you end the preview. The scene stores the director and its reference to the asset.

Move, trim, key, track, and duration edits use `Undo.RecordStructuralChange`, so Ctrl+Z reverts them. The asset is read-only in play mode.

The residency strip is under the ruler. Each bucket of the manifest is a bar, and a white tick marks a camera cut. While a preview or a director is open, the color shows how many entries of the bucket have their target level: green for all, yellow for some, and red for none. Without an open cutscene, the color shows the highest level of the bucket. A missing, stale, invalid, or unmatched manifest draws an orange marker over the timeline, because playback uses the approximate manifest. The manifest state is the same with and without a preview: with no preview, the panel computes the state that a session would select (`TextureResidencyBackend.GetManifestState`), which also checks that the baked textures are loaded. **Unmatched** ("does not match the scene") means that the hash is current but too many baked textures are not loaded; a new bake helps only when the assets moved or are outside the asset folders. A yellow line shows the cut at which the playback wait holds. The strip reads the levels of all manifest assets in one `IResidencyBackend.GetLevels` call for each frame, and decodes the visible buckets with a cursor. The panel computes the manifest state only after a bake, after a model import ends, or after edits from the panel stop for 0.25 s, so a clip drag runs it one time. The status line is cached and built again only when one of its values changes. The line above the strip shows the manifest state, the asset count, the pending T0 loads, the generation, the timed-out waits, and the rejected texture requests. A bake does not record an undo step.

## Edit-Mode Preview

`CutscenePreviewHost` has this contract:

- `Begin(asset)` compiles the asset and shows position zero at the first tick.
- `Seek` stores a target. The last seek before a tick wins.
- `Tick` applies an edit and a seek, then evaluates once.
- `NotifyAssetEdited` asks for a recompile at the next tick. The position, the rate, and the transport state stay. The position is limited to the new duration.
- `End` gives the camera back to the viewport, destroys spawned instances, and restores every recorded value. `KeepState` and `ForceRestoreAll` have no effect on a preview.

All host calls must run on the update thread. `EditorImGuiUI.EnqueueSceneEdit` moves a panel request to that thread.

Edit mode is not a stopped world. `RuntimeWorldHost.BeginEditModeAsync` turns off physics and the game mode, and then starts the world. The world ticks, and `PostUpdateFrame` runs `ProcessDirtyTransforms`, so a transform that the preview writes during `UpdateFrame` is flushed in the same frame.

The preview does not mark a scene as changed, and it stops the undo system from recording its writes. Because the values are live, these rules apply:

- Entering play mode ends the preview before the world snapshot.
- Closing the panel ends a preview after the panel was shown.
- A save of a scene or a world during a preview fails with an error that tells you to end the preview. `AssetManager.SaveGuard` does this check on all save paths. A save of a cutscene asset is allowed.
- A move of a bound node with the gizmo during a pause stays until the next evaluation. Add a key to keep it. `End` restores the original value.
- `End` removes the transform changes of bound nodes that the undo history recorded since `Begin`, because those entries hold preview values. Other changes and key edits stay. After a preview, Ctrl+Z cannot undo a gizmo move of a bound node that you made during the preview.
- A change of the world closes the preview and restores the values. The reason is in the diagnostics.

## Play A Cutscene

Assign `CutsceneDirectorComponent.Asset`, then call `OpenAsync`. The director registers its tick after input and before animation. Use `director.Player` for the transport, and call `Close` to restore the targets that have the `RestoreState` setting.

A director needs a binding resolver. It uses `BindingResolver` if the property has a value. If not, it uses the static `CutsceneDirectorComponent.DefaultBindingResolverFactory`. The editor registers this factory at startup in `CutscenePreviewSession.Initialize`, and the factory searches the root nodes of the world of the director. `CutsceneSceneBindingResolver` finds a scene object only under those root nodes. The world copy of play mode keeps the object identifiers of the edit world, and the object cache can hold the edit node, so the resolver does not use a cached node from another world. Another application must register its own factory. Without a resolver, the open fails and the reason is in `director.Diagnostics`.

Set `TargetViewport` to show the camera that the cut tracks select. The director claims the camera of that viewport until it closes.

A claim changes only the camera that shows the scene. The screen-space UI of the viewport stays on the camera from before the claim, so the editor panels and a player HUD stay visible. A gameplay system must hide a HUD itself if a cutscene must not show it.

## MCP Tools

| Tool | Arguments | Result |
|---|---|---|
| `cutscene_open` | `node_id`, `asset_path`, `close` | Opens a cutscene, or closes it when `close` is true. |
| `cutscene_seek` | `seconds`, `intent` (`jump` or `scrub`) | Moves the position and evaluates before the call returns. |
| `cutscene_play` | `rate`, `pause` | Plays at a rate, or holds the position. |
| `cutscene_status` | none | Reads the state. |

Each tool returns `open`, `mode` (`preview`, `director`, or `closed`), `asset`, `position`, `state`, `duration`, `rate`, `compileCount`, and `diagnostics`. Times are in seconds.

While a cutscene is open, each tool also returns `audioClock`: the clock `mode`, `fallback`, `muted`, `differenceMs` (the heard position minus the clock position before the correction, from the last play step that read the clock), `reads` (the number of play steps that read the clock), `hardResyncs`, and `latencyMs` (the output latency of the last reading). The same values are on `CutscenePlayer`: `AudioClockDifference`, `AudioClockReadCount`, `AudioHardResyncCount`, and `AudioClockLatencyNanoseconds`. The counts start at zero when the player is created, so a recompile of a preview resets them.

In edit mode, `cutscene_open` starts a preview. In play mode, it opens a director, and `asset_path` is not available. Without `node_id` or `asset_path`, the tool uses the selected node, and then the only director in the world.

The tools run on the update thread. A capture after `cutscene_seek` shows the new time, because the transform flush runs later in the same frame.

```text
cutscene_open { "node_id": "<director-node-id>" }
cutscene_seek { "seconds": 2.5 }
capture_viewport_screenshot { "output_dir": "<absolute-capture-folder>" }
cutscene_open { "close": true }
```

## Limits

- The panel has no split, snap to other clips, or multi-select.
- The panel has no buttons for event tracks, property tracks, audio tracks, or simulation control tracks. Add them in the asset.
- A property track supports only `float`, `Vector3`, and `Quaternion` members.
- An audio track decodes on the update thread, in the director tick. A clip with no audio proxy has no scrub sound, and a jump starts its sound after the decoder seek on the update thread: the clock does not count the seek time, but the frame of the seek is long. A clip with a current proxy plays the proxy at once and seeks in the background (see [Tier Change](#tier-change)). The proxy is mono, so a stereo clip is mono until the crossfade.
- The first refill after the first restart on a listener allocates about 700 bytes, with or without a proxy: the listener buffer pool makes its fifth `AudioBuffer`, because the restart keeps four buffers in the queue and the refill takes one more before the pool has one. Later restarts, play steps, and scrub grains do not allocate.
- An Ogg Vorbis seek decodes and drops the frames up to the target, because the NVorbis seek is not exact. A forward seek decodes from the current position, so its cost grows with the distance. A backward seek decodes the file again from its start, so its cost grows with the target time. Both cost about 1.1 to 1.6 ms per second of skipped 48 kHz stereo audio: 140 ms for a jump to 120 s and 310 to 390 ms for a jump of 240 to 280 s. A WAV seek is immediate.
- NVorbis 0.10.5 allocates on the heap for each decoded packet (new sample arrays, floor data, and packet objects). Our decoder adds no allocation, but Ogg Vorbis playback allocates about 21 KB for each 2048 decoded frames. At 48 kHz stereo this is about 0.5 MB for each second of audio, or about 8 KB for each 60 Hz frame. A seek allocates the same amount for each skipped second: about 53 MB for a jump to 120 s and 106 to 122 MB for a jump of 240 to 280 s. WAV playback and WAV seeks do not allocate. Use WAV for long cutscene audio if the garbage collector cost matters.
- `AudioData` imports WAV, Ogg Vorbis, and MP3. A FLAC import returns false, because no decoder supports FLAC.
- Bindings created by the panel use the object ID and a node path. Root node names must stay the same for the path fallback.
- The default resolver is registered by the editor only.
- Textures and audio sources have a residency backend. The bake records mesh assets for the T0 report, but no backend loads them.
- A texture outside the game and engine asset folders gets a key of its full path, so a manifest with such keys matches only on the machine and in the folder of the bake. A renamed or moved texture file, and a renamed node on a sub-mesh path, also change the keys. The content hash does not see these changes. For textures, the open finds the mismatch and uses the approximate manifest with one `Unmatched` diagnostic; bake the manifest again. Sub-mesh keys have no check, because no mesh backend exists.
- The object cache is global to the process and not to the world of the cutscene. An older instance of a texture that the scene does not draw can also get requests, until it is destroyed.
- The check after a load runs one time, when the backend reports that the imports ended. Assets that load later with no import (for example a streamed scene) do not start a new check; a preview refresh or a new open does.
- Under memory pressure, the session releases only the holds outside the request window. The holds in the window stay until the window moves, and the streaming budget fit lowers those textures.
- A stale manifest makes the whole timeline approximate. The hash does not find which range changed.
- The `Cutscene` budget profile limits are measured on OpenGL only, and on OpenGL they do not change the refine time (see [Budget Profiles](../../architecture/rendering/texture-streaming.md#budget-profiles)). On OpenGL, each texture upload of a cold jump adds about 5 to 9 ms to one frame, with either profile.
- The T0 budget default (64 MiB) is checked against one scene only: Sponza (37 textures, 25 sub-meshes) needs 15.6 MiB, and most of it is mesh data.
