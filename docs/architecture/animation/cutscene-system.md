# Cutscene System

This document describes the design of the cutscene timeline system: the ownership of its parts, the tick order and the clock, the residency of cutscene assets, and the invariants and limits of each part. The [cutscene guide](../../developer-guides/animation/cutscenes.md) tells how to author, preview, play, and drive a cutscene.

## Goals And Model

A cutscene is a time-indexed sequence of tracks. Every sampled state is a function of the cutscene time, so play, seek, scrub, and reverse playback use one evaluation path. Events are the only side effect, and they never change state that a seek needs.

- `CutsceneAsset` holds the tracks, the clips, the bindings, the residency manifest, and the audio proxies. It holds no runtime state.
- `CutsceneCompiler` validates an asset and builds `CompiledCutscene`, the time index of the clips. The player queries the index for the clips that are active at a time, into a buffer of `CompiledCutscene.MaxActiveClips` entries that the player allocates once.
- `CutsceneTime` stores time in flicks (705,600,000 for each second), as a 64-bit integer. Frame, sample, and second conversions use integer math, so a position does not drift.
- `CutsceneBindingTable` maps the binding slots to scene nodes. `CutsceneStateSnapshot` records the original value of each written member, so a stop or a close can restore it.

## Tick Order And The Clock

### Frame Order

`CutsceneDirectorComponent` registers its tick only while a cutscene is open, in `ETickGroup.Normal` at `DirectorTickOrder` (300000): after input and before animation. The tick calls `AdvanceFrame` with the dilated update time. One director frame runs these steps in this order:

1. `CutsceneResidencySession.BeginTick`.
2. `CutscenePlayer.Tick`.
3. `CutsceneResidencySession.CompleteTick`, which updates the planners for a tick that was not a play step.
4. `CutsceneVrCameraRouter.Update`.
5. `CutsceneOpenSequence.OnHostFrame`, which reads the residency state after the planner update of this frame.

The director reads the residency session before the tick and the VR router after the tick, because an event handler in the tick can close the director. `CutscenePreviewHost` uses the same order in edit mode, with no VR router step.

### Player Tick

`CutscenePlayer.Tick(deltaSeconds)` runs these steps:

1. It takes the restart time of the clock audio track from the last tick (see [Audio Clock](#audio-clock)).
2. It gives the transport state to the audio and video tracks before any evaluation. Audio streams only in forward playback at rate one with no gate hold. Video decodes forward in forward playback, and shows keyframes during a scrub seek or reverse playback.
3. If a seek is pending, the player resolves only the last seek, evaluates once at the target, publishes the camera, raises at most one `Discontinuity`, dispatches the events by the seek policy, and ends the transport step.
4. Otherwise, in the `Playing` state, the clock advances by the delta minus the restart time. Then the audio track disciplines the clock. The discipline comes before the evaluation and the event dispatch, so both use the final position of the step.
5. The playback gate (the residency session) can limit the play step, so a held frame never shows the state after the hold position.
6. The evaluators run in this order: transform, animation clip, activation, camera cut, camera property, property, audio, and video.
7. A camera change or a hard resync raises one `Discontinuity`. Then the events of the step fire, after the evaluation, so a handler sees the state of the new position.
8. After the transport step, `SimulationControlEvaluator.ApplyTick` applies the simulation policies for the discontinuity of the tick, or for a stop since the last tick. A simulation reset therefore occurs only in a tick, never in `Seek` or `Stop`.
9. The video tracks are serviced (`VideoTrackEvaluator.Update`), also in a tick with no evaluation.

A handler can call `Stop`, `Seek`, or `Play`. The event dispatcher keeps a transport version, so a stop or a seek ends the rest of the tick.

### Clock Modes

`CutsceneClock` has three modes (`ECutsceneClockMode`):

| Mode | Behavior |
|---|---|
| `Wall` | The delta times the rate moves the position. |
| `AudioDisciplined` | Wall time moves the position. The heard audio position corrects it through `Discipline`. |
| `Manual` | Only `SetPosition` changes the position. The manifest bake uses this mode. |

A player whose cutscene has an audio track with `DrivesClock` starts in `AudioDisciplined` mode. A correction moves the position by at most `MaxSlewFraction` (5 percent) of the last advance step. A difference above `HardResyncSeconds` (100 ms) makes the clock jump to the audio position (a hard resync). The first valid reading after a sound restart moves the clock in one step when the difference is 100 ms or less, and this is not a hard resync. The audio track owns the reading, the warm-up rules, and the fallback to `Wall` mode (see [Audio Clock](#audio-clock)).

Play dispatch keeps a high-water mark: a play step never fires an event at or below the highest position that playback reached, so a clock correction never fires an event twice. A seek, a hard resync, and a stop move the mark.

### Discontinuities

`CutscenePlayer.Discontinuity` is raised at most once in a tick, also when a cut and a jump occur in the same tick. `CutsceneDiscontinuity` carries the old and the new position, the seek intent, and the kind:

| Kind | Cause | Resets |
|---|---|---|
| `Full` | A seek that changes the position or the camera, a camera cut during playback, or a stop that moves the position or the camera. | Temporal render history, auto exposure, the simulations, and the VR rig fade. |
| `ClockResync` | A hard resync to the audio inside one shot, with no camera change. | Temporal render history only. Auto exposure and the simulations continue. A cut in the same tick makes the discontinuity `Full`. |

`ActiveCameraChanged` is raised before `Discontinuity` in the same tick, so the camera router claims the new camera before the handler resets the viewport.

## Discontinuity Resets

`CutsceneCameraRouter` owns a `CutsceneDiscontinuityHandler`. At each `Discontinuity`, after the router claimed the camera of the new shot, the handler resets the target viewport once. The handler does not allocate, because a scrub raises a discontinuity in each step, and it changes the camera with no property notifications.

| Reset | Kinds | Effect in the Default, Advanced, and RVC pipelines |
|---|---|---|
| `XRViewport.InvalidateTemporalHistory(publishNotifications: false)` | `Full`, `ClockResync` | Advances `XRCamera.TemporalHistoryEpoch`. The camera loses its previous view-projection (camera motion vectors), and the frame view history marks the view as having no valid history. TAA and TSR history then reset. Spatial hash AO, the only temporal AO pass, follows that history for mono views. |
| `XRCamera.ResetAutoExposureHistory()` | `Full` | Auto exposure does not read the epoch, and it blends from the exposure of the previous frame. The reset makes the next update set the metered exposure in one step, on the GPU path (OpenGL, Vulkan, and WebGPU) and on the CPU path. The reset records the new camera epoch. `VPRC_ExposureUpdate` passes the epoch that the view history ledger recorded at the capture of the rendered frame, so a frame from before the reset that still renders does not use it, and the first new frame uses it once. This guard applies only where the desktop view history ledger authors history. A frame with no ledger epoch (output sequence 0, view history authoring off, a stereo pass, or the front-buffer CPU path) counts as a new frame, so on those paths a frame from before the reset can still use it; the reset never stays blocked. On the CPU path, one snap request waits for its luminance result; if no result comes in 1 s (for example with no current renderer), a new request starts. A camera that has no post-process state yet gets one before the reset, so the first cut to a shot camera also snaps. The shot camera keeps its exposure state while the viewport renders it with the kept pipeline of the claim (see [camera claims](../rendering/default-render-pipeline-notes.md)). |

A scrub seek is a `Full` discontinuity, so each step of a ruler drag requests one exposure reset, and exposure snaps to the metered value in each frame of the drag. The request does not allocate.

The handler does not reset GI history (radiance cascades, ReSTIR reservoirs, surfels, and DDGI probes), the previous model matrix and skin palette of each mesh, the Advanced deformation history, or the RVC temporal cache. These have no reset hook for a view discontinuity. Without a target viewport, no render state resets.

### Camera Claim Exposure State

During a claim, the viewport renders the shot camera with the kept pipeline of the claim, and the camera uses its default post-process state for that pipeline. A post-process query with no pipeline from outside the render (for example on the update thread) also uses the kept pipeline. When the default state binds to another pipeline of the same type, each stage keeps its backing object. So the automatic exposure history and a pending exposure reset stay, exposure adapts on a shot camera, and the reset of a `Full` discontinuity snaps it. `XRCamera.ResetAutoExposureHistory` creates no state and no render pipeline: if the camera has no color grading state yet, the reset waits in `CameraPostProcessStateCollection`, and the first state that the render creates or binds gets it, so the first cut to a camera also snaps. The end of the last claim is a cut back to gameplay: the viewport removes the resets of the claimed cameras that no frame used, and resets the exposure of the returning camera, so that camera does not continue from the exposure that the shot cameras left in the viewport. See the camera claim rules in the [default render pipeline notes](../rendering/default-render-pipeline-notes.md).

### Simulations

A simulation keeps state from frame to frame, so it is not a function of the time. `SimulationControlTrack` sets the policy of the physics chains and the particle emitters of its node after a `Full` discontinuity or a scrub step: `SettleFromReset` or `WarmUp`, with a fixed seed. The player applies the policies at the end of `Tick`. One discontinuity gives one reset of each simulation. During a scrub, each step resets the simulations and they hold the reset pose, until playback at a rate near one, `EndScrub`, or a jump. A tick with no discontinuity and no hold does no simulation work. The [cutscene guide](../../developer-guides/animation/cutscenes.md#simulation-control-tracks) gives the per-target behavior.

## Residency

`CutsceneResidencyPlanner` decides which level of each asset must be resident, and by which time, around the playhead. The levels are T0 (proxy), T1 (coarse), and T2 (target). The planner sends requests to an `IResidencyBackend` and does no IO itself. The director and the editor preview run it through a `CutsceneResidencySession` (see [Residency In Playback](#residency-in-playback)). `TextureResidencyBackend` is the texture backend, `AudioResidencyBackend` is the audio backend, `VideoResidencyBackend` is the video backend, and `MeshResidencyBackend` is the mesh backend.

- **Input:** a `CutsceneResidencyManifest` holds a shared asset table, the kind of each asset (`EResidencyAssetKind`: `Texture`, `Mesh`, `Audio`, or `Video`), and `ResidencyBucket` entries in time order, with no overlap. Each `ResidencyEntry` gives an asset index, a target level, and a screen coverage. A bucket can mark a camera cut at its start. The kind is per asset and not per entry, because one asset has one kind. The manifest is serializable: the properties have setters, and the planner constructor calls `Validate`. `SelectKind(kind)` makes a manifest of one kind.
- **Compression:** the buckets are delta-compressed. A key bucket (`IsDelta` false, the default) lists all of its entries. A delta bucket (`ResidencyBucket.CreateDelta`) lists only the entries that are new or changed against the bucket before, and the asset indices in `Removed`. The first bucket and each bucket at a camera cut must be key buckets. `CutsceneResidencyManifestBuilder` rounds each coverage to 1/128, merges adjacent buckets with equal entries (not across a cut), and writes a key bucket at each cut, at least every 4 seconds (`DefaultKeyInterval`), and where a delta is not smaller than the full list. `CutsceneResidencyBucketCursor` decodes any bucket: a move starts at the key at or before the bucket, or continues from the current bucket, and allocates nothing after its constructor. The planner reads its window and the hold targets through one cursor. A synthetic 10-minute bake with 300 assets stores 23,400 entries instead of 240,000, in 720 buckets instead of 2400.
- **Calls:** call `Open` one time. It requests T0 for each asset. Then call `Update(position, rate, seek, deltaSeconds)` one time in each frame on the update thread. `seek` is null when no seek occurred. A backend reports complete work with `NotifyCompleted`, from any thread. The next update applies it and raises `LoadCompleted`.
- **Plan:** an update plans again only when the playhead goes into another bucket, the window covers other buckets, the rate changes, a seek occurs, the dwell gate changes, or a load completes. Otherwise it allocates nothing and sends nothing. The window is 5 seconds ahead at rate 1, scaled by the absolute rate, in the direction of travel, plus 0.5 seconds behind. At rate 0 (a pause), the window is the forward window of rate 1, so a pause does not cancel the prefetch. The planner requests one level above the resident level at a time. Requests sort by level, then by the time until the playhead needs them, then by screen coverage in descending order. A bucket behind the playhead sorts after the buckets ahead of it. Running work of the current generation stays while the window needs its level or a higher one, so a load that completes during an update is not cancelled. A jump, an asset that leaves the window, and a closed dwell gate cancel the running work.
- **Jump:** a `Jump` increments `Generation` and cancels the work of older generations. A late result of an older generation runs no callback.
- **Scrub:** a `Scrub` sends nothing above T0 until the playhead stays within 50 ms of timeline time for 120 ms of wall time. A new drag cancels the T1 and T2 work that did not complete. A `Jump` does not use this gate.
- **Eviction:** `Evict(maxCount)` releases T1 and T2 data. First it releases the assets outside the request window, farthest from the playhead first. Then it releases the assets in the window, farthest deadline first. It never releases T0. `Evict(maxCount, outsideWindowOnly: true)` releases only the assets outside the window. `CutsceneResidencySession` calls that form under memory pressure (see [Residency In Playback](#residency-in-playback)). An eviction allocates nothing.
- **Backend contract:** `IResidencyBackend.Cancel` on a complete ticket releases the data that the ticket holds. Set the level that `GetLevel` reports before the call to `NotifyCompleted`. A level that only a cache supplies, with no ticket, is not held.
- **Playback wait:** `PlaybackWaitEnabled` is off by default. When it is on, forward play that crosses a camera cut sets `IsHoldingPlayback` until the next shot has its target levels or `PlaybackWaitMaximumSeconds` (default 1 second) passes. The caller holds the clock at `PlaybackHoldTime`. A jump, a scrub, and reverse play never hold, and they end a hold. A pause keeps a hold, and the paused time does not count toward the maximum wait. `PlaybackWaitTimeoutCount` counts the waits that reached the maximum.
- **Close:** `Close` cancels all work and releases all levels, T0 included. After it, a completion runs no callback and `Update` does nothing.
- **Textures:** `TextureResidencyBackend` sends the levels to the imported texture streaming manager as explicit residency requests (see [Texture Streaming](../rendering/texture-streaming.md#explicit-residency-requests)). T0 is the texture preview, T1 is the first mip with a largest side of at most `CoarseMaxDimension` (default 512), and T2 is the full source size. The texture quality setting and the VRAM budget can lower T2. A request is not visibility and does not pin the texture. A cancel of a complete ticket releases the hold, and the texture returns to visibility-driven residency. `GetLevel` reports the highest level of a ticket whose mip is resident now.
  - Create it with an `AssetManager` or with a `Func<Guid, XRTexture2D?>`. The `AssetManager` form finds a texture by a runtime ID in the loaded assets and then in the object cache (`XRObjectBase.ObjectsCache`), because a texture that a model import creates is a live object but not an asset of the manager. Then it finds the textures of a stable key (see [Asset Keys](#asset-keys)) through an index of the live textures. A texture that is destroyed or queued for destroy is not found. The index scans the object cache at its first miss and keeps the key of each texture that it saw. It scans again only after `BeginSelection`, so a manifest selection scans at most one time, also when many keys miss (see the next items for the two other cases). The backend resolves each asset one time for each selection and uses the same textures for `CanResolve` and `Request`. It works on textures that are already loaded. It does not load assets.
  - One key can have more than one live texture, for example the eager and the deferred texture of one import. A request then goes to each of them, and `GetLevel` reports a level only when it is resident for each of them. The order is the runtime-ID order of one index build; it can change at the next start, which does not matter, because every texture gets the request. A texture that streaming does not accept is left out of the request; `PartialRejectedTextureCount` counts it, and the first one of each asset gives one warning.
  - Within one selection, a kept result with a destroyed texture (for example after a reimport while a preview is open) is resolved again, and the first such result lets the index build one more time. At a selection, the index also builds again when the object count changed since its last build, so a new duplicate of a key that hits is found.
  - `CanResolve(assetId)` is true when the asset is a live texture now. `AreAssetsLoading` is true while model imports are active (`AreModelImportsActive` gives the same value for the shared manager). `IsUnderMemoryPressure` is true while the last streaming evaluation found VRAM budget pressure (`ImportedTextureStreamingManager.IsUnderBudgetPressure`): the budget fit gave a texture less than its desired size, the streamed textures used more than the available budget, or the Vulkan allocator budget stopped promotions. The per-frame limits of a budget profile are not memory pressure, because they limit the work of a frame. A release would add demotion transitions to that work.
  - Call `AttachPlanner(planner)` before `planner.Open()`, so that the backend can report complete work. Call `SetPlayhead(position, rate)` before each `planner.Update`, so that request deadlines become frame deadlines (`EstimatedFramesPerSecond`, default 60). Without a playhead, requests have no deadline.
  - By default it holds the `Cutscene` texture streaming budget profile. The profile is global to the streaming manager, so the backends of one manager share it with a reference count: the first backend selects `Cutscene`, and the last `Dispose` selects `Default` again. Two open directors therefore keep the profile until both close. The `Cutscene` limits are provisional engine settings.
  - The backend rejects a request when the asset is not a loaded texture, when streaming does not track the texture, or when the source size for T1 is not known yet. It logs a warning and counts the rejection in `RejectedRequestCount`.
- **Audio:** `AudioResidencyBackend` handles the audio clip sources that have a proxy, by the key `CutsceneResidencyAssetKeys.ForAudioSource`. T0 is the proxy; it is part of the cutscene asset, so it is resident at once. A stale proxy never plays, so the backend rejects T0 for it with no log (the track gives the one diagnostic); T1 and T2 of its source still load. T1 and T2 open the full decoder of the source file on a background task and seek it near the deadline: the file frame of the clip that plays at the deadline, or the first frame of the next clip. The ticket holds the open decoder until the planner cancels it, so the file data is in the cache of the operating system before the playhead gets there. The track opens its own decoder for playback. The backend sets the level before `NotifyCompleted`. A cancel of a complete ticket closes its decoder, and a cancel of running work makes the task close its decoder at its end and report nothing. `BuildManifest()` makes the manifest of the audio planner from the timeline: one asset for each source, buckets at the clip edges, and T2 with the coverage 1 for each clip range, because sound has no screen coverage. A request for an unknown asset is rejected and counted in `RejectedRequestCount`; a failed open or seek is logged and counted in `FailedLoadCount`.
- **Video:** `VideoResidencyBackend` handles the video clip source files, by the key `CutsceneResidencyAssetKeys.ForVideoSource` (the portable reference of the file, or its full path outside the asset folders). Each source has one media session (a queue of 1 frame) and a small warm set (a `VideoFrameCache` of 5 frames, `SourceCacheCapacity`), so a source is not cached two times. The warm set guarantees this: the frame of the deadline of each complete level is pinned, so no warm frame can evict it, and it stays until the planner cancels that level; `GetLevel` reports a level only while its frame is held. At most three such frames exist for a source (one for each level), and they stay also above the byte budget. The warm frames are best effort: they use the free slots and at most 16 MiB of unpinned bytes (`SourceCacheBudgetBytes`: two 1080p frames, no 4K frame), and a warm frame that does not fit is skipped or evicted first. The budget is hard for the warm set (`keepOneFrame: false`): an unpinned frame larger than the budget is not stored, and when a cancel unpins or removes a frame, the pooled free buffers and the oldest unpinned frames go until the unpinned bytes fit again. So a source holds at most the pinned deadline frames plus 16 MiB. T0 opens the session and decodes the keyframe at or before the file time of the deadline; it stays resident while the cutscene is open. T1 decodes the keyframe at or before its deadline. T2 decodes the exact frame of its deadline and the 2 frames after it (`WarmFrameCount`), so the warm set holds the frames that a jump needs first. The file time of a deadline is the file time of the clip that shows at the deadline, or the first frame of the next clip. The loads run on background tasks, one at a time for each source, and each load waits at most 10 s (`LoadTimeoutSeconds`). A video track copies a frame from this cache on a miss of its own cache (`TryCopyFrame`), with no decode. The backend sets the level before `NotifyCompleted`. A cancel of a complete ticket removes its frames from the cache, unless another complete ticket holds the same frame, and the session of a source closes when no ticket of the source is left. A cancel of running work makes the task drop its frames and report nothing. `BuildManifest()` makes the manifest of the video planner from the timeline: one asset for each source, buckets at the clip edges, and T2 with the coverage 1 for each clip range, because the bake does not see video surfaces. A request for an unknown asset is rejected and counted in `RejectedRequestCount`; a failed open, seek, or frame wait is logged and counted in `FailedLoadCount`.
- **Meshes:** `MeshResidencyBackend` handles the sub-meshes of the scene, by the key `CutsceneResidencyAssetKeys.ForSubMesh`. The levels are LOD tiers (`SubMeshLodTiers`): T0 is the coarsest LOD, T1 the LODs between, and T2 LOD 0. A sub-mesh with one LOD has only LOD 0, which is T2. The default backend (`MeshResidencyBackend.CreateDefault`) searches the roots of the bound nodes and the scene roots of their worlds, and searches again at each selection (`BeginSelection`).
  - A cooked sub-mesh of codec version 2 keeps its coarsest LOD inline, so T0 is resident at once. Each other LOD is a separate `lod/<key>` archive entry (see [Mesh LOD Payloads](../assets/cooked-asset-aot-and-io.md#mesh-lod-payloads)). A request for T1 or T2 reads the entries of that tier that are not resident on a job thread, and checks their length, checksum, bone set, and blendshape names. The backend publishes the prepared meshes at the next frame boundary, in `SetPlayhead` (or `PublishPending`) on the update thread: it sets `SubMeshLOD.Mesh`, and each `RenderableMesh` of the sub-mesh makes a renderer for the LOD. The LOD becomes selectable, and its LOD registration version advances, when that renderer is ready on the active render backend; until then the lower resident LOD keeps drawing. Then the backend completes the ticket. The render thread does no disk IO and no hash work for this.
  - A LOD that one placement loaded is resident for all placements of the sub-mesh, with a reference count. A cancel of running work drops the prepared mesh, so the residency does not change. A cancel of a complete ticket releases the LODs that the backend published and that no other ticket holds: the LOD leaves the selectable set first, and its renderer goes to the deferred destruction queue. A LOD that was resident before the backend (a load with the default `All` policy, an editor sub-mesh, or an older cooked sub-mesh) is never released, so the world outside the cutscene does not change.
  - A LOD that fails to load warns one time for the life of the backend (`WarnedLodCount`), and `FailedLoadCount` counts each failed attempt. One `PublishPending` publishes at most `MaxPublicationsPerFrame` LODs (default 2), so a jump spreads the renderer setup and the GPU scene atlas registration over frames. Each registration costs time in proportion to the atlas size on the collect swap, which the render thread waits for.
  - An editor sub-mesh and an older cooked sub-mesh (codec version 1) have all LODs resident: `GetLevel` gives T2, and a request completes at once. `LegacySubMeshCount` counts the version 1 sub-meshes, and the session gives one diagnostic with the text "Cook again for progressive mesh loading". A LOD that fails to load stays not resident, its ticket does not complete, and one warning names the sub-mesh, the LOD, and the reason.
  - `RenderableMesh` holds only resident LODs in `LODs`. `LodTableCount`, `GetLodResidency(index)`, `IsLodResident(index)`, and `CurrentLodIndex` describe the full LOD table, and `RenderableLOD.Residency` gives the tier of a resident LOD. `UpdateLOD` walks the full table with the same rule as before and takes the resident LOD nearest to the requested index; at equal distance the coarser LOD wins. `ForcedMinimumLod` keeps the request at that index or coarser, for diagnostics and tests. A LOD that is published after construction resets the palette seed state at its first selection, and takes the current blendshape weights by name.

### Residency In Playback

`CutsceneDirectorComponent` and `CutscenePreviewHost` each own one `CutsceneResidencySession` while a cutscene is open:

- **Open:** `CutsceneResidencySession.TryOpen` creates the backend, selects the manifest, and opens the session. A current, valid baked manifest is used as it is. A missing, stale, or invalid manifest (`ECutsceneManifestState.Invalid` also covers a hash that could not be computed) gives the approximate manifest and one diagnostic. The selection also calls `IResidencyBackend.BeginSelection` and resolves each texture of the manifest one time (`CanResolve`, true by default). If more than `CutsceneManifestMatch.MaxUnresolvedTextureFraction` (10%) of the textures of a current baked manifest are not found, the content hash is still current, but the manifest does not match the scene: the state is `ECutsceneManifestState.Unmatched`, and the session uses the approximate manifest with one diagnostic. For a small manifest one missing texture can be enough (1 of 9). While `IResidencyBackend.AreAssetsLoading` is true, a missing texture can still load, so the session keeps the baked manifest (`IsWaitingForAssets`) and selects again one time at the first update after the loading ends. The new selection replaces the planner, so it waits while the planner holds playback at a cut. After `AttachPlayer` with another player (a preview recompile), the stored compile and bindings are old, so the selection waits for the next `Refresh` of the host. Textures that are not found at or below the fraction are not sent to the backend; one diagnostic gives their count, and `UnresolvedTextureCount` holds it. A manifest diagnostic is added again only when its reason changes, for example a key mismatch and then an edit, not when a refresh gives the same reason. A residency failure (no backend, or an exception from the factory, the selection, or the open) gives one diagnostic, disposes the backend, removes the gate, and the cutscene opens and plays without residency. Mesh assets go to a mesh backend with its own planner, `CutsceneResidencySession.MeshPlanner`: `Create` and `TryOpen` take an optional mesh factory (`Func<CompiledCutscene, CutsceneBindingTable, IResidencyBackend?>`), and the default is `MeshResidencyBackend.CreateDefault`. Its manifest is the mesh assets of the selected manifest that the backend finds. It is made again at a `Refresh` only when the mesh assets of the manifest changed, it never holds playback, and memory pressure does not release its data. Mesh assets that the backend does not find, or that have no mesh planner, give one diagnostic with the cause. The session sends only the texture assets to the texture backend. Audio assets go to an audio backend with its own planner, `CutsceneResidencySession.AudioPlanner`: `Create` and `TryOpen` take an optional factory, and the default (`CreateDefaultAudioBackend`) makes an `AudioResidencyBackend` for a cutscene with audio proxies. The audio planner gets each playhead update, opens and closes with the session, and is made again at a `Refresh` only when the audio inputs changed (the audio clips, the proxies, or the audio assets of the manifest), so a refresh after a model import keeps the open decoders. A refresh makes the new audio part before it changes anything, so a throw leaves the session as it was. It never holds playback, and memory pressure does not release its data. Video assets go to a video backend with its own planner in the same way, `CutsceneResidencySession.VideoPlanner`: `Create` and `TryOpen` take an optional video factory, and the default (`CreateDefaultVideoBackend`) makes a `VideoResidencyBackend` for a cutscene with video clips when a media backend is registered. The session gives that backend to the video tracks of the player (and takes it back at a player change and at close), and a refresh makes it again only when the video clips or the video assets of the manifest changed. A manifest with video assets and no video planner gives one diagnostic, as for audio. If the manifest has audio assets and no audio planner exists, one diagnostic gives their count and the cause: no backend was made (no proxies, or the factory gave none), or no proxy matches an audio clip. The constructor calls `backend.AttachPlanner(planner)`, and `Open(player)` calls `planner.Open()` and sets the session as `player.PlaybackGate`.
- **Frame:** the host calls `BeginTick`, then `player.Tick`, then `CompleteTick`. A play step updates the planner through the gate, before the player evaluates. Any other tick updates it in `CompleteTick` with `player.LastTickSeek`: the intent of a resolved seek, or `Jump` for a `Stop` since the last tick. The player passes the same value to the gate, so `Stop(); Play();` before a tick is a `Jump` too. A hard audio resync is a correction of normal play, so the planner sees it as a play step. A paused or scrubbing player reports rate zero. Each update calls `backend.SetPlayhead(position, rate)` first. A paused preview that does not tick the player calls `UpdateIdle`, so the dwell gate of a scrub can open. A preview loop wrap is a jump seek, so the planner sees it as a `Jump`.
- **Preview recompile:** an edit recompiles the preview. The session, the backend, and the budget profile stay, and `AttachPlayer` moves the gate to the new player at once. The manifest selection (hash, approximate manifest) and the planner swap (`Refresh`) wait until no edit came for `CutscenePreviewHost.ResidencyRefreshDelaySeconds` (0.25 s), so a clip drag does not repeat that work in each frame. A refresh adds a manifest diagnostic only when the manifest state changes.
- **Memory pressure:** after each planner update, the session reads `IResidencyBackend.IsUnderMemoryPressure` (false by default). Under pressure, it calls `Evict(PressureEvictionsPerUpdate, outsideWindowOnly: true)` at most one time for each new budget evaluation (`IResidencyBackend.MemoryPressureFrameId`): at most 4 assets release their T1 and T2 data, outside the request window first and farthest from the playhead first. A release demotes only after the demotion cooldown, so the flag can stay set for some evaluations. A flag whose evaluation does not advance, for example when no viewport collects, is stale and releases nothing. T0 data stays. Data in the window also stays, because the streaming budget fit already lowers those textures, and the next plan would request their levels again. `PressureEvictionCount` counts the releases. With no pressure, the check allocates nothing.
- **Close:** the director closes the session at `Close`, at component deactivation, at `OnEndPlay` (world or scene end), and at destroy. The session closes the planner and then disposes the backend. Then the player restores the targets.

### Manifest, Keys, And Hash

- <a id="asset-keys"></a>**Asset keys:** a model import makes new runtime IDs for its textures and sub-meshes at each import, and the model has no stored ID. So the default collector records stable keys from `CutsceneResidencyAssetKeys`, not runtime IDs. A texture that is its own stored asset (its file has the asset extension) uses its persisted ID. A texture with a source file (`OriginalPath`, which a model import sets) uses a name-based GUID of the portable source reference (`game://` or `engine://`, from `AssetSerializationServices.Current.TryCreatePortableAssetReference`) and the sampler name, which is the cache identity of the importer. A path that is already portable is used as it is. The reference has `/` separators and upper case on every OS. A texture with no source path that is embedded in a stored asset uses its stored ID. Any other texture uses a key of its own file reference and sampler name. A sub-mesh uses a key of its place in the scene: the persisted ID of the scene that owns the root node, the node path from the root (each node name with its index among the siblings, or the scene roots, of the same name), the component index, and the sub-mesh index. The keys stay the same after a new import of the same model, on another machine, and in another project folder. A file outside the game and engine asset folders has no portable reference, so its key uses the full path; the bake reports the count of such keys in one diagnostic. A custom collector can use any ID that `IResidencyBackend` can resolve.
- **Cooked builds:** the content cook (`ProjectBuilder`) writes the `OriginalPath` of each asset in the cooked bytes (also the textures of a material, a texture that a source image backs, and live assets that the cooked asset references) as a portable reference, and writes no `FilePath` (see [Portable Source Paths](../assets/cooked-asset-aot-and-io.md#portable-source-paths)). A source path outside the asset folders fails the cook, and a check after the cook fails it if any machine path is left. A cooked build therefore computes the same texture keys as the editor, although it runs from another folder. A texture streaming restore resolves a portable `game://` or `engine://` `OriginalPath` against the asset roots before it reads the file.
- **Stale manifest:** `CutsceneManifestHash` hashes the duration, the restore setting, and the object graph of the bindings and the tracks: a stable type name (namespace and name, with no assembly name or version), then each public property with a public setter and no `YamlIgnore`, and each public field, in name order. A referenced asset, for example an animation clip, adds only its ID, so an edit inside that asset does not make the manifest stale. A .NET or engine upgrade does not change the hash; a rename or a move of a track or clip type does. A member value that the hash cannot read exactly (a dictionary, a delegate, a type object, or a value type with no settable member, such as `decimal`, `TimeSpan`, or `DateTime`) throws `NotSupportedException` with the member path, and playback reports an invalid manifest. A new member of such a type therefore cannot escape the stale check. It does not include the manifest, the hash, or the name. Any later change to the asset makes the manifest stale (`ECutsceneManifestState.Stale`), and playback then uses the approximate manifest for the whole timeline.
- **Approximate manifest:** `CutsceneApproximateManifest.Build` splits the timeline at each clip edge. A bucket holds the assets of the bound nodes, and their descendants, whose tracks have an active clip there. It uses the open poses and the camera of the active cut at its open pose. An asset at or above the target coverage, or with no camera, needs T2, and any other asset needs T1. It never drops an asset for its coverage, because the open pose can be wrong. It does not see objects that no track binds.

### Mesh LOD Payloads And Late LODs

The mesh backend depends on the split mesh LOD format. The format and the reader are in [Mesh LOD Payloads](../assets/cooked-asset-aot-and-io.md#mesh-lod-payloads), and the GPU route rules are in the [mesh LOD residency contract](../rendering/mesh-submission-strategies.md). In short:

- `SubMeshCookedCodec` version 2 keeps the sub-mesh fields, a LOD table of `SubMeshLodDescriptor` entries (counts, bounds, bone set hash, blendshape name hash, content key, payload length, and payload checksum), and the payload of the coarsest LOD inline. Each other LOD is a separate archive entry `lod/<content key>`. The reader checks the length and the checksum before it parses, and the hashes after. A bad LOD is rejected alone. The runtime never cooks again.
- `SubMeshLodPayloads.LoadPolicy` is `All` by default, so a normal world load makes every LOD resident. `ProxyFirst` reads only the inline LOD. `SubMeshLodPayloads.TryLoadLod` reads one entry later, on a job thread.
- The mesh backend reads and checks the payloads of a tier on a job thread. It publishes the prepared meshes at the next frame boundary on the update thread, at most `MaxPublicationsPerFrame` (default 2) in one `PublishPending`. The cap counts publications and not bytes, because each publication rebuilds the dirty GPU scene atlas tier on the collect swap, and that cost grows with the atlas size and not with the LOD size.
- Late-LOD readiness gate: a published LOD gets a new renderer, and the slot is not selectable (`SelectionReady` is 0). A render-thread coroutine calls `XRMeshRenderer.TryPrewarmForLodSelection` (the backend `IRenderPreparationState.TryPrewarmForSelection`, by default the program and buffer preparation) once in each frame. When it succeeds, the LOD becomes selectable, `LodRegistrationVersion` advances one time, and the coroutine ends. The coroutine also ends when the LOD leaves the table, gets another renderer, or the mesh retires. Until then, the CPU selection and the GPU registration keep the lower resident LOD. With a concrete render host, the coroutine always runs on the render thread, so the update thread never prepares backend state. With no host, the check runs inline. After 1800 failed attempts, one warning is written, and the LOD stays not selectable.

### Open Sequence And ReadyForInstantSeek

`CutsceneOpenSequence` opens a cutscene progressively on any `ICutsceneOpenHost` (the director and the preview host). It opens the host, which opens the residency session and requests T0 for each asset. It collects the T0 draws (`CutsceneProxyDraw`: each renderable mesh of the bound closure with its material override, or else the material of its lowest LOD, drawn by the renderer of the lowest LOD) and requests their programs through `ICutsceneProgramPrewarmer`. At the end of each host frame, it reads `CutsceneResidencySession.PendingProxyCount` and the program state of each T0 draw. When every T0 load completed and every T0 draw is ready, it sets `CutscenePlayer.ReadyForInstantSeek` and then requests the programs of the other LOD materials as lower-priority work.

- The sequence advances only in host frames on the update thread. It never waits for the render thread, and no caller may block on its task.
- T0 stays resident until the close, so a seek after the flag is true loads no T0 data.
- The program state of a T0 draw is `ECutsceneProgramState`: `NotStarted`, `Compiling`, `Ready`, `Failed`, or `NotSupported`. Only `Ready` counts as ready. `Failed` and `NotSupported` add one diagnostic for each draw that names the material and the reason, and the task completes with false when no draw still waits.
- The default prewarmer (`CutsceneBackendProgramPrewarmer`, one for each open) combines the uber variant build of the material with the backend draw readiness. One render-thread coroutine (through `RuntimeRenderingHostServices.Scheduling`) checks each draw in each frame and stores the result; the update thread reads only the stored results. While the uber variant of a material builds, the draw is `Compiling` and the backend is not asked, because the variant changes the program and the pipelines. Only `Failed` and `NotSupported` are final: a `Ready` draw is checked again in each frame, so a later relink or pipeline change makes it not ready again. A check that throws makes that draw `Failed` with the exception message. The coroutine ends when the open finishes, fails, or is canceled. It allocates nothing in a frame.
- The open sets `ICutsceneProgramPrewarmer.View` from `ICutsceneOpenHost.OpenViewport` (the viewport of the camera router) at each frame, so the readiness is measured against the passes of the cutscene camera, not the editor viewport or a shadow pass.
- A T0 draw that stays `NotStarted` or `Compiling` for `ProgramWaitWarningFrames` host frames (1800 by default) adds one diagnostic with the material, the renderer, the mesh submission strategy, the state, and the reason. The open keeps waiting; it never completes in silence.
- A preview recompile during the open makes a new binding table and new instances. The sequence sees the new table, calls `ICutsceneProgramPrewarmer.Reset`, and collects the draws again.
- `XRMeshRenderer.QueryDrawReadiness(material, renderOptionsOverride, view)` goes through the renderer facade to `IRenderPreparationState.QueryDrawReadiness` (`RenderDrawReadinessQuery`, `ERenderDrawReadiness`). With a headset or emulated VR output it also checks the stereo version and combines both (`RenderDrawReadinessCombiner`). OpenGL runs the non-blocking preparation (the compile and link queue, which polls `GL_COMPLETION_STATUS` with parallel shader compile), also for a material override through the per-material program step of the draw path, and reports a draw that still uses a temporary fallback program as compiling. Vulkan runs the program and buffer preparation under the recording lock (a program with a failed backend stage, or a material with no compatible vertex shader, is `Failed`) and gives the pipeline result of the last frame from `VulkanDrawReadinessRegistry`. The pre-recording admission prewarms the pipelines of each active request for every non-shadow pass context of the view that draws the pass of the material: a CPU mesh draw of the view is a template for the T0 renderer (`VulkanDrawReadinessTemplate`: the draw state is the render options of the T0 draw, or the render options override of the renderable, over the pass state of the pass context of the template (the draw enqueue stores it one time for each render pipeline instance, pass, and target while a request is active; `VulkanDrawReadinessRegistry.RecordPassState`), with the rules of `VulkanMeshDrawFixedState`; nothing comes from the material of the template; an override-material pass such as the depth-normal prepass uses its override material), a GPU-driven indirect draw of the material is checked as the real draw, and a mesh-task dispatch is ready when its requirement is admitted. The result is ready only when every required context is ready, and only for the program, link generation, shared pipeline retirement generation, and target signature that the frame measured: after a program swap, a relink, a pipeline retirement wave, or a target change (resize, MSAA), a published ready is `Compiling` until a frame measures again. The PresentNow readiness gate also runs the prewarm, so the T0 pipelines compile while the view warms up. A request ends when the open stops (`EndDrawReadinessQueries`), when its renderer wrapper is deleted or unlinked, or 2 s after the last query; the prewarm skips and drops a wrapper that is not active, unlinked, retired, or deleted, so it never makes programs or pipelines for it. The scratch collections of the prewarm are the thread-local recording scratch. A backend that does not implement the query gives `NotSupported`. With no render host, the query gives `Ready`, because no draw exists.
- The flag is false for a player that no sequence opened and for a host with no residency session. It is not checked again after it is true.

## Audio

The audio track streams its active clip with an `IStreamingAudioDecoder` and feeds the sources of its node through `AudioSourceComponent.EnqueueStreamingBuffer`. The [cutscene guide](../../developer-guides/animation/cutscenes.md#audio-tracks) gives the clip settings and the transport behavior.

### Audio Proxies

The manifest bake makes one `AudioProxyAsset` for each audio clip source file, so that the player can play sound in the same frame after a far jump, before the full decoder reaches the new position (see [Tier Change](#tier-change)).

- **Format:** standard IMA ADPCM, mono, 22050 Hz (`ImaAdpcmDecoder.ProxySampleRate`), 4 bits for each sample. It uses the 89-entry step table and the 16-entry index table. Each block starts with a 4 byte header: the first sample (a little-endian 16 bit value), the step index, and one reserved byte. Then each byte holds two codes, the earlier sample in the low nibble. A block holds 1017 samples in 512 bytes (`AudioProxyAsset.DefaultBlockSamples`, the standard block of mono 22050 Hz IMA ADPCM WAV files). That is 11,101 bytes for each second.
- **Seek:** each header stores the full decoder state, so `ImaAdpcmDecoder` decodes only the block of the new frame. A random-access read gives exactly the same samples as a sequential read. `Read` allocates nothing.
- **Encode:** `ImaAdpcmEncoder.Encode(mono, blockSamples)` rounds each sample to 16 bits and tracks the decoder state, so the error does not grow along a block. The step index continues from the block before; the first block starts with the step that is nearest to the first difference. A 440 Hz sine at half scale decodes with a maximum error of about 0.0095 and an RMS error of about 0.0037.
- **Source conversion:** `AudioProxyBuilder` reads any `IStreamingAudioDecoder` and mixes the channels to their mean. When the source rate is above 22050 Hz, a low-pass FIR filter runs first: a Hamming-windowed sinc with its cutoff at 0.45 times the target rate (about 9.9 kHz), with `16 * ceil(sourceRate / 22050)` taps on each side (65 taps for 44.1 kHz), scaled to a DC gain of one. Without the filter, a 44.1 kHz source would be a plain 2:1 decimation, and all content from 11 to 22 kHz (sibilance, cymbals) would fold back below 11 kHz. The filter is centered, so it adds no delay; it holds the first and the last sample at the ends. Then a linear resampler computes output frame `i` at source position `i * sourceRate / 22050` with integers, so the result is deterministic and does not drift. The builder keeps the mono result in memory until the encode, so it runs at a bake and not in a frame.
- **Data:** `AudioProxyAsset` stores `EncodedData`, `SampleRate`, `BlockSamples`, `FrameCount`, `SourceReference`, and `SourceContentHash` (the XxHash64 of the source file). YAML stores `EncodedData` as one base64 value. `CreateDecoder()` opens a decoder that reads the stored bytes without a copy.
- **Source reference:** the portable reference of the source file (`game://` or `engine://`). The bake finds the file with `AudioTrackEvaluator.ResolveSourcePath`, the same rule that playback uses. A file outside the asset folders keeps its relative `SourcePath` (relative to the cutscene asset). A proxy never stores a full local path, so a source with a full path outside the asset folders gets no proxy and one diagnostic.
- **Storage:** the bake gives the proxies to the caller, which stores them in `CutsceneAsset.AudioProxies` (embedded in the cutscene asset). Clips with the same source share one proxy. A later bake uses a stored proxy again when its source reference, its source hash, its sample rate, its block size, and its data length all match, and encodes the source again otherwise. A source that does not open gives one diagnostic. The proxies are not part of `CutsceneManifestHash`.
- **Manifest:** the bake lists each proxy as an `Audio` asset with the key `CutsceneResidencyAssetKeys.ForAudioSource(proxy.SourceReference)` and no bucket entries. Its T0 size is the length of `EncodedData`. The residency session sends these assets to `AudioResidencyBackend` (see [Residency In Playback](#residency-in-playback)).
- **Shared rules:** `CutsceneAudioProxySources` holds the rules that the bake and playback share: `TryGetSourceReference` (the reference above), `HashSourceFile` (the XxHash64 of the file), and `FindProxy` (the proxy of a reference, case is ignored).

### Tier Change

A clip whose source has a proxy in `CutsceneAsset.AudioProxies` uses two tiers. A clip with no proxy plays as before: a jump seeks the full decoder on the update thread, and a cutscene with no proxies plays exactly as before.

1. A restart outside the ring of decoded frames (a jump, or the first play at a time after zero) does not seek on the update thread. In the same frame, the track fills the queue from the proxy (T0) at the exact frame.
2. An `AudioDecoderSeekWorker` seeks the full decoder on a background task to a buffer start after the queue. The lead is at least 4 buffers (8192 frames, the queue of the restart). The first refill comes about one buffer after the restart, so a longer seek adds buffers for twice the estimated seek time beyond that buffer. The estimate is the larger of the measured time of the last seek of the decoder and, for an Ogg Vorbis decoder, 2 ms for each second of the target time (a backward Vorbis seek decodes from the start of the file). A cold Vorbis seek to 120 s therefore asks for 15 buffers. The update thread does not use the decoder while the worker has work. A newer jump cancels a seek that did not start, and makes the result of a running seek stale; the task then seeks to the newest frame. A seek that ends after its buffer passed asks again at a later buffer with twice the lead (at most 256 buffers).
3. At the first buffer boundary at which the full decoder is at the produced frame, `AudioTierCrossfader` crossfades from the proxy to the full decoder over 20 ms with equal (linear) gain: the full gain is `t = (k + 0.5) / n` and the proxy gain is `1 - t` for frame `k` of `n`. The sum of the gains is one.
4. The crossfader resamples the proxy (22050 Hz mono) to the rate and the channel count of the full decoder: full frame `f` is at proxy position `f * 22050 / fullRate` (integer math, linear interpolation), and each channel gets the same value. The bake puts proxy frame `i` at source position `i * sourceRate / 22050` with no filter delay, so the two signals are sample-aligned.

The queue keeps one format and one frame rate across the change, so the frame count of the audio clock does not change and the clock does not jump. The ring holds the frames that played, so a restart inside the ring (a resume) plays the same frames again. The two signals are coherent and sample-aligned, so equal gain keeps the level flat through the fade, with no step. (Equal power would be up to 3 dB louder in the middle of the fade and could clip.) If the background seek fails, the clip plays the proxy to its end and adds one diagnostic.

**Stale proxy:** when the track is created, the evaluator compares `SourceContentHash` of each proxy with the hash of its source file, one time. A file with the same length and write time uses a stored hash, so a preview recompile does not read it again. This is a heuristic: a file replaced with the same length and write time keeps the old hash. The cache holds at most 256 files and ignores case only on Windows and macOS. The first open reads each proxied source file in full on the creating thread. A proxy that does not match, or whose file cannot be read, adds one diagnostic and never plays. After a jump, that clip is silent until the full decoder is ready, and then fades in over 20 ms. A proxy whose data does not open gives the same result with its own diagnostic.

### Audio Clock

A cutscene with an audio track that has `DrivesClock` set (the default) starts its clock in `AudioDisciplined` mode. In each play step, after the clock advances and before the evaluation and the event dispatch, the player reads the heard position from the first such track of the last evaluation. The track reads the playback clock of its first source through `IAudioTransport.TryGetPlaybackClock`. The heard position is the frame count before the queue, plus the source position, minus the output latency. While that value is below the frame of the last restart, the listener does not hear the new queue yet (for example during the 300 ms NAudio output latency). The clock then stays on wall time with no correction, and this is not a loss of the clock: no diagnostic and no fallback. The same applies when the sources wait for a restart because their queues differ. A warm-up has a bound: if it lasts longer than the output latency plus 250 ms (and at least 500 ms) of play steps after the restart, the device does not reach the queue, and the player treats it as a lost clock, with the fallback and its one diagnostic below. The first valid heard position after a restart (a start, a seek, a resume, a return to rate 1, or a new listener) moves the clock to that position in one step, if the difference is 100 ms or less. During the warm-up the clock runs on wall time, so it is ahead of the sound by about the output latency. The step removes this offset at once. It is not a hard resync: it raises no `Discontinuity`, and the high-water mark below keeps a backward step from firing an event again. After that step, the clock moves toward the heard position by at most 5 percent of the frame step. When the difference is more than 100 ms, the clock jumps (a hard resync): the player raises `Discontinuity` with `Jump` intent and `ClockResync` kind (or `Full` kind if the camera also changed in that tick), and the events across the jump follow the seek policy of each track.

A restart runs in the tick: it seeks the decoder and decodes the new queue into the ring while the sources still play, then stops the sources, queues the decoded buffers, and plays. The sources are stopped only while the queue is copied and played, so a mixer update in that window (one OpenAL Soft period, about 20 ms) is less likely than one between a stop and a long decode. A batch play call (`alSourcePlayv`) does not help here, because a track has one source for each listener, and each listener has its own transport context. The sources start only at its end, so the player removes from the clock advance of the next tick the time that delayed the clock track: the restarts in service order up to and including the restart of the clock track. A restart of another track while the clock track plays on removes nothing. If no track drives the clock, nothing is removed. A long decoder seek therefore makes one long frame, but no hard resync. The removed time is wall time; it is not scaled by a time dilation. A track that becomes the clock track with no restart, for example when the clip of the earlier clock track ends, slews and does not step.

The clock reads the first source of the track, so only that source controls the clock reading and a restart of all sources. If the first source stops before the end of the data, all sources restart. The first such stop after a valid clock reading, for example after one long frame, does not count toward the warm-up bound. Later consecutive stops with no valid reading between them keep the warm-up time, so a first source that never plays reaches the bound and the fallback. Their restart time is not removed from the clock.

Another source that stops (for example, the source of a second listener) restarts alone, once. It starts at the buffer that the first source plays, so it can be up to one buffer (2048 frames) behind. It gets another restart only after it plays a buffer, or after a restart of all sources. This does not need a clock reading, so it also works on a track that does not drive the clock. A seek or a resume starts a new count of starves for the warm-up bound. If it stops again, the track adds one diagnostic for that listener and gives the source no sound until the next restart of all sources. The first source and the clock continue. After the sources play the last buffer of the clip and stop, the player does not read the heard position. The listener still hears the output latency there, so the value stays behind the clock.

Play dispatch keeps a high-water mark: a play step never fires an event at or below the highest position that playback reached. So a clock correction never fires an event twice. A seek, a hard resync, and a stop move the mark to the new position. Reverse playback followed by forward playback does not fire the crossed events again. A seek back does.

| Transport | Clock |
|---|---|
| OpenAL | `AL_SAMPLE_OFFSET_LATENCY_SOFT` from `AL_SOFT_source_latency`. Without the extension, there is no clock. |
| NAudio | The mixer position. The latency is the `DesiredLatency` of the `WaveOutEvent` output, which is an estimate. |
| WebAudio | No clock. |

If the transport has no clock, the player changes the clock to `Wall` mode, sets `CutscenePlayer.IsAudioClockFallback`, and adds one diagnostic. The clock goes back to `AudioDisciplined` when the transport reports a clock again, and also at a stop.

## Video

The video track shows its active clip on the `IVideoFrameTarget` of its node. `UIVideoComponent` is that target: `SubmitFrame` copies the frame into a back buffer, and the next render pass uploads it through `IVideoFrameGpuActions`. The [cutscene guide](../../developer-guides/animation/cutscenes.md#video-tracks) gives the clip settings and the transport table.

### Frame Cache And Memory

The frame cache of each track holds at most `VideoTrack.FrameCacheCapacity` frames (default 24, `VideoFrameCache.DefaultCapacity`) and at most `VideoTrack.FrameCacheBudgetBytes` bytes (default 64 MiB, `VideoFrameCache.DefaultBudgetBytes`), and always one frame. Each frame uses `width * height * 3` bytes. Slot buffers are made only when frames come; when the count or the byte budget is full, a new frame uses the buffer of the frame that was used least recently. The budget holds on every growth: after a resolution change, the cache drops the buffers that are too small (free slots first, then the frames used least recently) before it makes a larger buffer, and a buffer that is two or more times the frame size is made smaller. A clip change clears the cache and releases every buffer.

**Memory per source** (RGB24 frames: 1080p is 5.9 MiB, 4K is 23.7 MiB; native decoder frames are not counted):

| Part | Rule | 1080p | 4K |
|---|---|---|---|
| Track cache | 64 MiB budget, at least one frame | 10 frames, 59.3 MiB | 2 frames, 47.5 MiB |
| Track session buffers | queue of 2, plus the lent frame and the frame in decode | 4 frames, 23.7 MiB | 4 frames, 94.9 MiB |
| Residency deadline frames (pinned) | one for each held level, at most 3 | 3 frames, 17.8 MiB | 3 frames, 71.2 MiB |
| Residency warm frames and pooled buffers | hard 16 MiB budget for unpinned bytes | 2 frames, 11.9 MiB | 0 frames (one 4K frame is larger than the budget) |
| Residency session buffers | queue of 1 | 3 frames, 17.8 MiB | 3 frames, 71.2 MiB |
| `UIVideoComponent` surface | front and back buffer | 2 frames, 11.9 MiB | 2 frames, 47.5 MiB |
| Total | | about 143 MiB | about 332 MiB |

With no residency session, a 1080p source uses about 95 MiB and a 4K source about 190 MiB.

### Frame Lookup

The track first looks in its `VideoFrameCache`. A frame that covers the time (its time is at or before the time, and the time is before its end) shows at once and starts no decode. During a drag, a finished seek result of an older time shows when it is at or before the wanted time, so a keyframe decode that takes longer than a tick does not freeze the surface; a result after the wanted time (a backward drag) does not show. A forward drag never steps back: while the shown frame is at or before the wanted time, an older frame (a late exact frame or an older keyframe) does not show. A backward drag shows keyframes at or before its time. A miss asks the video residency backend for a copy (see [Residency](#residency)), and then asks the session for a seek. At most one seek of a track is in flight: newer times wait, and the track asks for the newest time when the seek ends. The track uses `IMediaStreamSession.RequestSeek` and polls `GetSeekState`, with no task, so a moving drag allocates nothing on the update thread. All decoding runs on the decoder thread of the session, so a tick never waits for it, and a result shows in a later tick. After the end of the file, forward playback does not seek again. `CutscenePlayer.Tick` services the tracks in each tick, also in a tick with no evaluation. A host that does not tick a paused player calls `CutscenePlayer.UpdateVideo` in each frame; the editor preview does this.

### Media Session Seek

`IMediaStreamSession.CanSeek` is true only for a session opened with `ClockDrivenPresentation` on a local file with a known duration and a video stream, because only the clock-driven loop runs seeks. A normal streaming session gives false. `SeekAsync(targetTicks, mode, cancellationToken)` returns a task; `RequestSeek(targetTicks, mode)` returns a request id with no allocation, and `GetSeekState(id)` gives `Pending`, `Completed`, `Cancelled`, or `Failed` (`LastSeekError` tells why). Both return at once; the decoder thread of `FFmpegStreamDecoder` does the work. One caller at a time may seek a session; the session takes the generation and posts the request under one lock.

- **Time line:** in the clock-driven mode, the start time of the video stream is zero, so a file with a non-zero start time plays from its first frame. A frame before the start (pre-roll or an edit list) keeps its negative time, so a keyframe seek never reports a time after its target.

- **Position:** the demuxer seeks to the keyframe at or before the target (`AVSEEK_FLAG_BACKWARD`), and the decoder flushes. If the first frame is still after the target, the seek starts again 1, 4, and 16 s before the target, and the last attempt starts at the stream start. So a keyframe seek never lands after the target, and a backward seek works.
- **Keyframe:** the session gets that frame, and the decoder pauses until the next seek.
- **Exact:** the decoder decodes forward until the next frame has a time after the target, and gives the frame before it, which shows at the target. The next frame time decides, not the frame duration, so a variable frame rate does not change the choice. Then the decoder decodes forward. If the file ends first, its last frame is the result.
- **Supersede:** a newer seek ends an older one as cancelled. A seek that did not start never runs; a running seek stops at its next frame. The session drops the queued frames at each seek call, and each frame carries the generation of the seek that the decoder runs, so no frame of an old position reaches the caller. The cancellation token works the same way.
- **Clock-driven mode:** the session releases a frame when its time is at or before the passed clock plus 40 ms, zero included, and never uses wall time. The decoder waits for queue space on the session lock (a dequeue, a seek, an open, and a close wake it; it does not spin) and does not drop frames, and it stays alive at the end of the file for a later seek. A stop cancels every request, also one that comes during the stop. `Close` after `Dispose` does nothing. The frame buffers come from a pool in the session: the data of a dequeued frame stays valid until the next dequeue call, seek, or close. With the reused RGB frame of the decoder, steady playback allocates no frame data. `UIVideoComponent` streams do not set this mode and keep their old behavior.

### Seek Accuracy

`VideoSeekTests` writes small clips at test time with the FFmpeg libraries of the project. The FFmpeg build has decoders and muxers but no encoders, so the clips hold raw RGB frames, or QuickTime Animation (qtrle) frames that the test writes by hand. Each clip has 50 frames at 25 frames per second (40 ms per frame, exact in every time base), and each frame is one gray level that gives its index. The packets have a key flag every 10 frames.

| Container | Codec | Exact seek | Keyframe seek |
|---|---|---|---|
| Matroska (`.mkv`, VFW mode) | raw | The frame of the target, also mid-frame, backward, first, and last | At or before the target. Raw video is intra-only, so FFmpeg marks every raw frame as a keyframe. |
| QuickTime (`.mov`, the MP4 demuxer) | raw | Same | Same |
| QuickTime (`.mov`, the MP4 demuxer) | qtrle (inter frames) | Same | The keyframe at or before the target, every 10 frames |
| AVI (`.avi`) | raw | Same | At or before the target |
| NUT (`.nut`) | raw | Same | At or before the target (NUT can use an earlier sync point) |

The other muxers of this FFmpeg build do not keep qtrle (Matroska and AVI lose its sample description; NUT rejects it), so the inter-frame keyframe check runs on QuickTime only. MP4 files use the same demuxer as QuickTime files; the MP4 muxer rejects raw and qtrle video (also in the experimental compliance mode), so no MP4 clip is written. A Matroska clip that starts at frame 10 gives frame 0 at time 0 and frame 7 at its time, so the start time is the zero. A normal (not clock-driven) session on a local file reports `CanSeek == false`. A live HLS playlist opens and decodes, and reports `CanSeek == false`.

## VR Modes

In VR, a cutscene never takes head tracking away from the user. No mode writes an eye camera or the head pose, and no mode changes the VR view mode, the VR render pipeline, or the desktop mirror mode. `CutsceneVrCameraRouter.Validate` checks the mode before the open changes anything, and a mode that cannot run fails the open with a diagnostic. The router never substitutes another mode. The [cutscene guide](../../developer-guides/animation/cutscenes.md#vr-camera-modes) gives the modes, the failure cases, and the rig origin setup.

`SpectatorOnly` shows the shot camera only on the desktop viewport. `RigAnchor` moves the rig origin with the shot camera, and needs a headset fade, which only OpenVR has (`RuntimeCutsceneVrHost.CanFadeHeadset` is true only while an OpenVR session renders and its compositor is available). `WorldScreen` is not supported. The `RigAnchor` router runs after the player tick in each frame:

- The rig origin moves to the world position of the shot camera, and turns to its heading on the horizontal plane. The rig stays upright: a pitch or a roll of the camera does not tilt the horizon. The camera node therefore marks the rig origin (the floor point of the user) for the shot, not the eye position.
- A cut, or a `Full` discontinuity, starts a fade to black over half of `CutsceneAsset.RigCutFadeSeconds` (default 0.5 s; it must be finite and greater than zero). The rig holds during this half. At black, the rig moves to the newest shot. Then the headset stays black for at least `CutsceneVrCameraRouter.BlackHoldRenderFrames` (2) render frames (`ICutsceneVrHost.RenderFrameId`), so the frames in flight with the old pose are not visible, and at most `MaximumBlackHoldSeconds` (1 s) if no frame renders. The hold counts the engine render frame (`RuntimeEngine.Rendering.State.RenderFrameId`), not VR submits. When the desktop and the eyes render at different rates (for example a split desktop with render workers), two engine frames are not always two eye submits. Then the headset fades back in over the other half. The desktop shows the new shot at once. More cuts during the fade to black move the rig once. A cut during the hold moves the rig again at black, with a new teleport and a new hold, and with no second fade to black. Each cut checks the rig origin again. If the head moved to another parent (for example at a pawn switch), the router puts the rig back, adds one diagnostic, and stops following. A `ClockResync` discontinuity does not fade.
- Between cuts, the rig follows the shot camera. In a gap between shots, the rig holds, and the next shot fades in again.
- At each rig move (and at the move back at the close), the router publishes a local-player teleport through `ICutsceneVrHost.TryPublishTeleport`, so spectator follow, calibration, and tracker code reset instead of seeing the jump as motion. The engine host calls `RuntimeVrState.TryPublishLocalPlayerTeleport`; the desktop composition (`DesktopVrServicesLease`, for a profile that allows VR) installs the typed slot `RuntimeVrState.TeleportPublisher` (`IRuntimeVrTeleportPublisher`), which publishes `EVrPoseDiscontinuity.Teleport` through `RuntimeVrDiscontinuityServices`. Without a publisher, the router adds one diagnostic. At the move, the router calls `ICutsceneVrHost.InvalidateEyeViewHistory`: the engine host invalidates the temporal history of the eye viewports, and of each eye camera that is not the active camera of an eye viewport, once each and with no property change events. At the end of the black hold, the router calls `ICutsceneVrHost.ResetEyeExposure` (`XRCamera.ResetAutoExposureHistory`). The exposure reset waits for the hold because an eye pass has no ledger epoch: any eye frame that renders after the reset can use it (see [Discontinuity Resets](#discontinuity-resets)), and a frame from before the move would set the exposure of the old place. These resets change no pose.
- The fade uses `IRuntimeOpenVrCompositor.TryFadeToColor`, the OpenVR compositor fade over the submitted image. The compositor animates it on wall time, so the router times its phases with `ICutsceneVrHost.TimeSeconds` and not with the cutscene clock. The director calls it on the update thread. That is safe: it is one client call to the compositor process, like the input and frame statistics reads on the update side, and it does not touch the render-thread submit state.
- At the close, the router puts back the local position and rotation that the rig origin had at the open. The headset goes black at once, the rig moves back, and the router publishes a teleport and invalidates the eye history. The cleanup ends in the close call. Then `ICutsceneVrHost.TryScheduleFadeInAfterBlackHold` keeps the headset black for the same hold, resets the eye exposure, and fades in over half of the fade time. The step (`CutsceneVrCloseFadeIn`) has two parts. The engine host runs a render part as a render-thread coroutine (`RuntimeEngine.AddRenderThreadCoroutine`), which ends the hold after the render frames, and an update part as an app-thread coroutine (`RuntimeAnimationHostServices.AddAppThreadCoroutine`), which ends the hold at the 1 s deadline, so a backlog of render jobs cannot keep the headset black longer. The first part that fades in wins, and the other part then does nothing. They allocate once, at the close. The step owns the headset only while `ICutsceneVrHost.FadeGeneration` has the value that the close recorded after its fade to black. Each fade call increments the counter, so when the next cutscene opens before the step runs, its fade to black changes the counter, and the step does no fade-in and no exposure reset. `TryFadeHeadsetIfGeneration` checks the counter and fades under one lock, because the render part and the update thread can both fade. The default animation host (with no application composition) runs an app-thread coroutine inline; the engine host is used only in a live VR session, where the composition installs the real scheduler. If the host cannot schedule it, the headset fades in at once and the router adds one diagnostic. A close during a fade, or during the hold, also ends with the scene visible.
- No fade call throws: `ICutsceneVrHost.TryFadeHeadset` returns false when the runtime does not accept the fade, and the router also treats an exception from a host as a failure. The router checks `IsInVR` and `CanFadeHeadset` in each frame. The engine host reports `CanFadeHeadset` only while the session runs on OpenVR, the OpenVR render path is active, and the compositor is live (`IRuntimeOpenVrCompositor.IsAvailable`). When a check or a fade fails, the rig goes back at once, the router adds one diagnostic, and the rig stays there for the rest of the cutscene. The engine has no SteamVR quit event, so after SteamVR exits the router finds the loss at the next frame through these flags, the compositor handle, or a failed fade.
- The close restores the rig in a `finally` block, and the director runs the router detach inside its own `try`/`finally`, so a fade failure never skips the player stop, the camera release, or the binding disposal.
- A transport stop or the end of playback keeps the rig at the last shot. Only the close puts the rig back.
- A frame without a fade change, including a frame that waits during a fade, does not allocate.

## Invariants

- **No render-side disk IO.** The planner does no IO. Backends read files on job threads or background tasks. The mesh backend reads, checks, and parses LOD payloads off the render thread, and the render thread does no disk IO and no hash work for a publication.
- **Payload before publication.** A mesh LOD is complete and checked before the backend publishes it, and a published LOD is selectable only after its renderer is ready on the active backend. A texture mip publishes on the render thread only, after the GPU receipt and a generation check. A backend sets the level that `GetLevel` reports before it calls `NotifyCompleted`.
- **T0 is the floor.** The planner never releases T0 before the close. The lowest resident mesh LOD stays in the GPU scene atlas, and a selection clamps to resident, selectable LODs.
- **No CPU readback on zero-readback routes.** The cutscene runtime adds no GPU readback. The mesh backend gets its targets from the manifest, not from the GPU LOD request buffer. One exception exists outside the cutscene code: with `StreamMeshLodsOnDemand` on (off by default), the request buffer drain still reads back while a cutscene is open.
- **No per-frame allocations.** A frame with no plan change, a scrub step, a discontinuity reset, a held simulation, a video drag, and a VR frame with no fade change do not allocate on the update thread. The known allocations are: one coroutine closure for each late-LOD publication, the video cache slot buffers when the cache grows, about 700 bytes at the first refill of a listener, and the packet allocations of the NVorbis decoder.
- **One evaluation path.** A seek stores a target, and the next tick evaluates once at the last target. Sampled tracks use only the time.
- **Fail loudly.** A mode, a backend, or a manifest that cannot run gives a diagnostic. The VR router never uses another mode, and a cutscene with no residency backend opens without residency and with one diagnostic, unless the host installed `InstallUnavailable`.

## Known Limits

- **Vulkan cold-cut hold.** On Vulkan, the first draw of a new late-LOD renderer is still a cold mesh admission in the frame loop. PresentNow rejects frames while it is cold, so after a cold jump the window shows the previous image for about 0.6 to 1 s, and up to about 2.5 s when the T2 program is also cold. The readiness gate keeps the lower LOD selected, but it spreads the LOD switches over frames, and each switch records cold descriptor work again.
- **No Vulkan video upload.** Only OpenGL implements `IVideoFrameGpuActionsBackendCapability`. On Vulkan the surface gets `NullVideoFrameGpuActions`, so a video track decodes and seeks but shows nothing.
- **Texture refine limited by the decode gate.** The OpenGL and Vulkan texture residency backends decode at most two textures at a time (`MaxConcurrentStreamingDecodes`). A cold jump in Sponza refines in about 2 s on OpenGL and 5 to 7 s on Vulkan, where the dense upload and publication service is the main limit. The `Cutscene` budget profile does not change this.
- **Vulkan readiness needs a view pass of the material.** The Vulkan prewarm takes its pass contexts from the operations of the cutscene view in each frame. A view that draws no non-shadow pass of the material in that frame (for example, a forward material in a view with no forward draw) gives no context, so the T0 draw stays `NotStarted` and the timeout diagnostic names it. Light shadow passes are not part of the readiness.
- **Single-level GPU registration for model components.** A model component owns the render info of its renderable meshes, so a render command of a model registers its command mesh as one LOD level. GPU LOD selection is off for those commands, and progressive residency works through the CPU selection, which clamps to resident LODs.
- **Archive loading of v2 models only in the editor or tests.** Separate `lod/` entries resolve through the configured published archives (`PublishedArchiveRegistry`) or a registered `DirectoryLodPayloadSource`. No launcher is configured to load models with `ProxyFirst` from archives, and a NativeAOT launcher rejects a cooked `Model`. The default load policy is `All`, so normal world loads and director spawn bindings make every LOD resident.
- **Publication cost.** Each late-LOD publication rebuilds a GPU scene atlas tier with a full face-list copy on the collect swap. The cap of two publications in each frame spreads this cost but does not remove it. The publication queue is first-in, first-out, not in deadline order.
- **Mesh residency.** The mesh planner never holds playback, and memory pressure does not release mesh LODs. The readiness probe prepares the mono renderer only, and the OpenXR eye path does not treat a cold late LOD as a retry.
- **`WorldScreen` unsupported.** No component shows a completed camera capture on a world surface, so the mode fails the open in VR.
- **`RigAnchor` on OpenVR only.** OpenXR has no headset fade in this engine, so the mode fails the open on OpenXR. No headset run has confirmed the fade timing, the black hold in each desktop view mode, or the eye exposure after a cut.
- **Cook check.** `ProjectBuilder` does not call `CutsceneCookCheck`, so a shipping cook does not reject a cutscene with a missing or stale manifest.
- **Manifest staleness.** A stale manifest makes the whole timeline approximate, because the hash does not find which range changed.
- Textures, audio sources, video sources, and sub-meshes have a residency backend. The bake does not record video assets; the video planner uses the manifest from the timeline.
- A texture outside the game and engine asset folders gets a key of its full path, so a manifest with such keys matches only on the machine and in the folder of the bake. A renamed or moved texture file, and a renamed node on a sub-mesh path, also change the keys. The content hash does not see these changes. For textures, the open finds the mismatch and uses the approximate manifest with one `Unmatched` diagnostic; bake the manifest again. A sub-mesh key that the mesh backend does not find gives the unrouted mesh diagnostic, but it does not make the manifest `Unmatched`.
- The object cache is global to the process and not to the world of the cutscene. An older instance of a texture that the scene does not draw can also get requests, until it is destroyed.
- The check after a load runs one time, when the backend reports that the imports ended. Assets that load later with no import (for example a streamed scene) do not start a new check; a preview refresh or a new open does.
- Under memory pressure, the session releases only the holds outside the request window. The holds in the window stay until the window moves, and the streaming budget fit lowers those textures.
- **Audio decode cost.** A clip with no proxy seeks on the update thread. An Ogg Vorbis seek decodes up to the target, and NVorbis allocates for each decoded packet. The [cutscene guide](../../developer-guides/animation/cutscenes.md#limits) gives the measured costs.
- **Physics chain root.** A transform track bound to the root bone of a physics chain writes the root in each tick, so the chain stays straight during playback. Bind the track to a parent node of the chain.
- **Scrub hold.** A simulation holds its reset pose only while a scrub seek comes in each frame. The editor ruler sends one; a scrub with gaps between seeks simulates between the steps.
