# Browser WebGPU asynchronous luminance

The WebGPU engine host exposes task-based RGB luminance reads for engine 2D and 2D-array textures and for a region of the next complete presented canvas frame. The legacy `CalcDotLuminanceAsync` and `CalcDotLuminanceFrontAsync` callbacks adapt those tasks. `CalcDotLuminanceFrontAsyncCompute` uses the same actual GPU reduction; it does not silently substitute a CPU screenshot or CPU pixel loop. The synchronous `CalcDotLuminance` overloads remain unsupported because waiting on a WebGPU map from the browser owner thread would deadlock or stall the renderer.

Reduction and mip-generation kernels are canonical engine compute recipes, cooked and hash verified like other engine shader artifacts. Optional `luminance-reduction`, `luminance-reduction-2d`, and `luminance-mipmap` identities are validated against their exact source-texture, storage, and parameter-uniform ABIs before world activation. An unused world need not package them. A request missing the kernel it needs fails explicitly. The separate 2D reduction avoids binding a one-layer texture as `2d-array` on a WebGPU compatibility device. No auto-exposure pipeline pass is enabled by this work.

The C# host owns request shape, weights, mip selection, resource admission and a four-million-texel budget. The JavaScript backend owns the native WebGPU two-dispatch lowering: 16×16 tiles produce GPU partial sums and one workgroup reduces them to one float. It uses the renderer's pipeline cache and the existing generation-stamped readback tickets. At most four luminance operations and 32 MiB of extra reduction resources can coexist; canvas snapshots also remain within the readback ticket budget. The only CPU data transfer is the final four-byte scalar, and completion is asynchronous. Disposal, cancellation, stale renderer sessions and stale surfaces invalidate tickets.

Texture RGB values are loaded through the texture's typed WebGPU view. Linear RGBA8 and RGBA16F retain their linear values. For a strict legacy sRGB read, a GPU texture-to-texture copy moves the selected encoded texel(s) from `rgba8unorm-srgb` to [copy-compatible](https://www.w3.org/TR/webgpu/#texture-copy-compatible) `rgba8unorm`, so reduction observes encoded normalized components as desktop `GetTextureImage` does. The separate authored base-average API retains decoded linear sRGB semantics. Alpha does not influence the dot product. Every array layer receives equal weight. Invalid RGB or a nonfinite final result fails the task rather than returning a plausible number.

Legacy `genMipmapsNow == false` reads the first texel of the smallest authored/allowed mip from each layer. With `genMipmapsNow == true`, a bounded GPU compute pass regenerates each needed mip level into packed GPU storage and copies it into the original texture's actual mip chain before the scalar reduction, all in one ordered submission. The default-enabled OpenGL 2D detail-preserving formula is ported for eligible linear RGBA8/RGBA16F 2D textures; arrays and other admitted formats use a per-layer box downsample. [OpenGL 4.6 §8.14.4](https://registry.khronos.org/OpenGL/specs/gl/glspec46.core.pdf) does not mandate a particular filter for ordinary `Generate*Mipmap`, so cross-driver bit-exact generated values are not promised. The 2D OpenGL path's fixed 16-byte `GetTextureImage` result is invalid for a selected mip larger than 1×1; the browser counterpart keeps the named `ScalarMipUnavailable` rejection for that existing contract limitation, while array reads request one texel per layer at non-scalar selected mips. Separate `ReadEngineAverageLuminanceAsync` overloads provide an explicitly linear GPU RGB average of the base mip without mutating its chain. Front-canvas reduction does not depend on texture mips.

Canvas regions use engine bottom-left coordinates and are converted to top-left copy coordinates. After the optional kernel is lazily prepared, a pending front request attaches to the next accepted, fully submitted canvas frame of the same surface generation, before browser presentation. The first request can miss frames while its shader pipeline compiles; a resize during that delay rejects it. The actual capture shares the screenshot producer-validation gate. Because canvas presentation is currently opaque, `withTransparency` cannot recover alpha; luminance measures displayed RGB in presentation space. A visible but frozen canvas request expires after five seconds, and hiding the page cancels pending requests.

Texture requests capture the resource handle and production ticket before lazy shader preparation, then revalidate recording, both values and the wrapper's current allocation immediately before dispatch. A new frame producing into the same texture or an authored mip/format change during that await invalidates the request rather than returning stale contents.

The original reduction-only slice passed a narrow `XREngine.Runtime.Rendering.WebGPU` Release build, JavaScript syntax, a canonical 42-shader cook, and an 84-asset engine-effects package. The authored RollingBall Editor→Browser publisher probe passed with its separate 15-shader catalog, which omitted compute artifacts. The new 2D/sRGB/mip-generation slice passed a narrow WebGPU Release graph build with zero warnings and errors (`Build/_AgentValidation/20261001-225000-lit-surface/ui-shaders/luminance-mip-narrow-build.log`), static JavaScript syntax and diff checks, and a full canonical engine shader cook with 44 artifacts including all four compute identities (`ui-shaders/engine-cook-mip.log`). Independent frozen-source review found no further concrete blockers after its stale-source completion check was incorporated. Live GPU behavior still needs qualification. Live checks should compare constant color, asymmetric sRGB-versus-linear color, a multi-layer array, non-1×1 authored mip, generated mips with standard and detail-preserving modes, non-power-of-two dimensions, canceled/hidden/resize requests, and a large bounded reduction. Confirm both front overloads use a GPU dispatch and only transfer four result bytes.
