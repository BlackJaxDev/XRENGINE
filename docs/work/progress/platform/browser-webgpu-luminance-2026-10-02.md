# Browser WebGPU asynchronous luminance

The WebGPU engine host exposes task-based RGB luminance reads for engine 2D and 2D-array textures and for a region of the next complete presented canvas frame. The legacy `CalcDotLuminanceAsync` and `CalcDotLuminanceFrontAsync` callbacks adapt those tasks. `CalcDotLuminanceFrontAsyncCompute` uses the same actual GPU reduction; it does not silently substitute a CPU screenshot or CPU pixel loop. The synchronous `CalcDotLuminance` overloads remain unsupported because waiting on a WebGPU map from the browser owner thread would deadlock or stall the renderer.

The reduction kernel is a canonical engine compute recipe, cooked and hash verified like other engine shader artifacts. The optional `luminance-reduction` identity is validated against an exact source-texture, partial-storage, result-storage and parameter-uniform ABI before world activation. An unused world need not package the kernel. A request in a world without it fails explicitly. No auto-exposure pipeline pass is enabled by this work.

The C# host owns request shape, weights, mip selection, resource admission and a four-million-texel budget. The JavaScript backend owns the native WebGPU two-dispatch lowering: 16×16 tiles produce GPU partial sums and one workgroup reduces them to one float. It uses the renderer's pipeline cache and the existing generation-stamped readback tickets. At most four luminance operations and 32 MiB of extra reduction resources can coexist; canvas snapshots also remain within the readback ticket budget. The only CPU data transfer is the final four-byte scalar, and completion is asynchronous. Disposal, cancellation, stale renderer sessions and stale surfaces invalidate tickets.

Texture RGB values are loaded through the texture's typed WebGPU view. An sRGB texture is decoded to linear values by `textureLoad`; linear RGBA8 and RGBA16F retain their linear values. Alpha does not influence the dot product. Every array layer receives equal weight. Invalid RGB or a nonfinite final result fails the task rather than returning a plausible number. Legacy `genMipmapsNow == false` reads the first texel of the smallest authored/allowed mip from each layer, matching the desktop array/Vulkan read location. Legacy `genMipmapsNow == true` requires a 1×1 base texture and otherwise rejects with `MipmapRefreshUnsupported`, because it would need to regenerate the mip chain as on desktop. The strict legacy read rejects sRGB textures with `SrgbReadUnsupported`: [OpenGL image readback](https://registry.khronos.org/OpenGL/specs/gl/glspec46.core.pdf) returns encoded component groups, while [WebGPU shader reads](https://www.w3.org/TR/webgpu/#texture-formats) apply sRGB decoding. The 2D OpenGL path's fixed 16-byte `GetTextureImage` result also means a selected mip larger than 1×1 is invalid there; the browser counterpart rejects it with `ScalarMipUnavailable`, while array reads request one texel per layer. Separate `ReadEngineAverageLuminanceAsync` overloads provide an explicitly linear GPU RGB average of the base mip, including sRGB decoding, without generating or mutating a mip chain. Front-canvas reduction does not depend on a texture mip chain.

Canvas regions use engine bottom-left coordinates and are converted to top-left copy coordinates. After the optional kernel is lazily prepared, a pending front request attaches to the next accepted, fully submitted canvas frame of the same surface generation, before browser presentation. The first request can miss frames while its shader pipeline compiles; a resize during that delay rejects it. The actual capture shares the screenshot producer-validation gate. Because canvas presentation is currently opaque, `withTransparency` cannot recover alpha; luminance measures displayed RGB in presentation space. A visible but frozen canvas request expires after five seconds, and hiding the page cancels pending requests.

Texture requests capture the resource handle and production ticket before lazy shader preparation, then revalidate recording, both values and the wrapper's current allocation immediately before dispatch. A new frame producing into the same texture or an authored mip/format change during that await invalidates the request rather than returning stale contents.

Validation so far: narrow `XREngine.Runtime.Rendering.WebGPU` Release build succeeded with zero warnings and zero errors; `node --check` passed for touched browser modules; a narrow ShaderCooker invocation packaged the canonical reduction artifact. A full canonical engine-shader cook packaged 42 artifacts including both `luminance-reduction` and `packed-skinning` compute identities, with nine raster pipeline artifacts. The existing engine-effects recipe then prepared successfully, and BrowserContentCooker published both compute identities in an 84-asset package. The authored RollingBall Editor→Browser publisher probe passed with its separate 15-shader catalog, which omitted compute artifacts, establishing a second publisher non-regression path. Live GPU behavior still needs qualification. Live checks should compare constant color, asymmetric sRGB-versus-linear color, a multi-layer array, non-1×1 authored mip, non-power-of-two front region, canceled/hidden/resize requests, and a large bounded reduction. Confirm both front overloads use a GPU dispatch and only transfer four result bytes.
