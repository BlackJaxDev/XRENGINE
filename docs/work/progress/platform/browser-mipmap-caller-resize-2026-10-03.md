# Mipmap caller-thread resize boundary

`Mipmap2D.ResizeAsync`, `InterpolativeResizeAsync`, and `AdaptiveResizeAsync` previously used `Task.Run` in every host. On a caller-thread/browser host, that sent CPU image-codec work outside the configured job pump. The deferred action also read the mipmap's current unmanaged `DataSource`, which could have been replaced or disposed before the worker reached it. `CubeMipmap` fans these APIs out over its faces with `Task.WhenAll`.

Caller-thread hosts now copy the source pixels into an owned `RuntimeImage` at request time and schedule the existing codec resize through `RuntimeWorkScheduler.Jobs`. The returned task awaits the job and releases the snapshot after it finishes, including fault and cancellation. A private revision invalidates queued work after another resize request or an accepted relevant property mutation. Publication also verifies the original data-source identity, disposal state, length, address, dimensions, pixel format/type, and internal format. This catches externally owned source disposal and final metadata changes made with property notifications suppressed. A disposed source is rejected before copying its pixels. Superseded work completes as canceled before publishing. Once publication begins, it retains the existing synchronous `SetFromImage` property observer/veto behavior. Desktop hosts keep their prior `Task.Run` path. This does not install an image codec or substitute CPU processing for a GPU request.

The input is a request-time snapshot. In-place writes to an existing data-source allocation do not carry a revision signal and are not detected; the resize uses the captured pixels. Notification-suppressed metadata changes that restore all captured values before dispatch likewise cannot be detected. Callers must serialize source mutation and disposal with snapshot creation; this does not make `Mipmap2D` or `DataSource` generally thread-safe. `DataSource.IsDisposed` is read-only and ignored by MemoryPack and YAML; existing data writers and ownership/disposal behavior are unchanged.

Publication retains the existing nontransactional setter sequence. A reentrant observer can change properties during `SetFromImage`, and a resize requested by that observer can be canceled by the remaining setter changes in the ongoing publication. Property vetoes likewise retain their synchronous results; cancellation guards are checked before publication, not between its setters.

The caller pump's elapsed-time budget cannot preempt a synchronous codec call once dispatched. A host that needs CPU resizing must register an `IRuntimeImageCodec`; the current browser composition registers none, so a nonempty-image request faults at codec admission. Empty-image dimension-only requests do not require a codec. The parent texture's disposal is not tracked here because `Mipmap2D` has no `Dispose` contract; data-source disposal and replacement are checked.

Validation uses the unchanged production methods and the registered Magick codec. The ignored `scratch/mipmap-caller-boundary` probe under the existing task run compares standard, bilinear, Lanczos, and adaptive output bytes with each synchronous counterpart, then exercises deferred execution, property vetoes, replacement, disposal, supersession, empty-image dimensions, scheduler shutdown, and `CubeMipmap` face fan-out with single-face cancellation and codec failure. The targeted Rendering and probe builds completed with zero warnings/errors, and all 29 probe checks passed. Logs are under the same run's `logs/`. This is a source/runtime probe, not a browser page test.

Independent review reproduced publication after external-source disposal and a notification-suppressed internal-format change, then verified their cancellation after the state checks above. An isolated checkout of baseline tree `cd4f79ed09f1c995633c528d832f6f34f4575c15`, overlaid with only `DataSource.cs`, `Mipmap2D.cs`, and this note, passed the original 29 checks and 16 additional review checks. The review covers source length/address changes, already-disposed inputs, owned/external disposal semantics, request-time pixel snapshots, snapshot/output disposal on success and codec failure/invalidation, reentrant publication, and missing-codec admission. Data, Core, Rendering, Magick, and both probes built with zero warnings/errors under the shared build lock. Six serialized output comparisons remained byte-for-byte identical: DataSource MemoryPack and cooked bytes, Mipmap2D MemoryPack bytes, DataSource YAML, and the DataSource/Mipmap2D cooked type schemas. Reproduction and validation evidence is in `Build/_AgentValidation/20261001-225000-lit-surface/logs/mipmap-review-before-run.log` and `logs/mipmap-isolated-*.log`; the isolated source and driver are `scratch/mipmap-review-2227` and `tools/build-mipmap-review.sh` under that run.

The first non-square comparison exposed an unrelated existing Magick codec behavior: a 4×4 source requested at 2×3 throws when Magick's aspect-preserving `Resize` produces a different size and the codec attempts to read the requested rectangle. The focused comparisons use square extents, and the codec is unchanged.
