# Asset manager direct-source boundaries

The asset manager's runtime catalog remains the authority for packaged identities. Its `LoadAsync` overloads enter `LoadFromRuntimeSourceAsync`, which reads and publishes the dependency closure through the captured source and source epoch. Synchronous requests can use a published catalog asset. An unloaded catalog path still requires the asynchronous catalog loader.

A browser, caller-thread owner, runtime catalog, or source that does not support synchronous reads no longer probes or creates host asset directories while the asset manager is constructed. Configured path roots remain path identities, and path setters do not create directories for those owners. An owner with direct host-file capability retains its existing directory discovery, metadata/cache initialization, watcher setup, and file behavior.

Once an existing desktop owner successfully binds a runtime catalog, it remains a catalog owner after unbind. Unloaded `Load` and `LoadAsync` requests then report `AssetSource.CatalogUnavailable` until a compatible catalog is rebound; they cannot reopen host files through that retired owner. Rebinding keeps the fixed virtual roots and starts a new source epoch. The original desktop watcher subscription remains retired.

Unloaded direct-source `Load` and `LoadAsync` requests on a nonblocking owner fail before file existence checks, remote download admission, or job scheduling. Already published, live assets remain available through the synchronous and asynchronous path caches. ID-to-path lookup can use a resident asset and skips metadata-directory enumeration without direct file capability. Catalog membership, type and teardown checks still govern cached catalog identities. The generic noncatalog async source interface has byte-read methods, but the current file loader's direct codecs, YAML reference resolution and third-party importers require host-file paths; it is not a substitute for the cooked catalog loader.

Explicit direct-file frontends report `AssetSource.HostFileUnavailable` when that capability is absent: metadata synchronization and metadata-file creation, partial YAML prefab planning, direct file deserialization, published archive configuration, streaming/cache authority import, variant import, authoring save, remote jobs that must read or persist operating-system files, and enabling host-file watchers. A deferred cache import rechecks before touching the file. Pure path construction and in-memory serialization remain separate from these gates. Catalog writes retain `AssetSource.ReadOnly`; unloaded catalog-prefab partial YAML planning retains `AssetSource.PartialYamlUnavailable`. Direct cooked and authored desktop file formats are unchanged.

Host-file watcher subscriptions retain their original source identity and source epoch. An owner whose source changes to a catalog drops later callbacks before reload, metadata synchronization or auto-import. Changed-file callbacks retain the same owner across their awaited reload and check it again before publishing follow-on notifications. A catalog bind followed by unbind cannot revive a desktop watcher copied under the old epoch. This does not cancel an already admitted desktop reload atomically.

Remote `SendLocalCopy` requests reject unavailable host-file access before consulting the job provider. Direct-file loads recheck admission after every remote-download outcome and before dispatching their local job. A valid noncatalog `RequestFromRemote` response can still deserialize and publish entirely in memory. It retains the initiating source and epoch, decodes in an independent object-publication scope, and rejects retirement or cancellation before publishing the decoded graph.

Remote response publication reserves its owner for a finite synchronous operation without holding the owner publication gate while constructors, property handlers, object-publication hooks, or `AssetLoaded` callbacks run. During this reservation, `BindRuntimeSource`, `UnbindRuntimeSource`, and `Dispose` report `AssetSource.PublicationPending` immediately; callers may retry after publication and its callbacks finish. Disposal also invalidates an outstanding decoded response by advancing the owner epoch. Reentrant disposal reports `AssetSource.TeardownPending` rather than waiting on its own cleanup callbacks.

Failed remote publication removes only the failed root's cache entries and path-container attachment, preserving any replacement entries. Its ownership ledger releases newly decoded objects, constructor defaults, and deferred allocations made by post-load callbacks without destroying or reparenting pre-existing dependencies. Cleanup failures follow the original publication error in an aggregate exception. An ownership ledger whose destruction failed is retained for a later disposal retry; a new catalog cannot bind until that cleanup succeeds. This is a remote-response boundary; it does not redesign the existing catalog publication path.
