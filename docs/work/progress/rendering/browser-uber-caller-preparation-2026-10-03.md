# Browser Uber variant caller preparation

Updated: 2026-10-03. This records the shared material request boundary; it is not a browser page or WebGPU output acceptance.

`XRMaterial.RequestUberVariantRebuild` and its edit debounce use an asynchronous host delay followed by a caller-job submission when the browser or caller-thread scheduler is active. The host's bounded job pump owns source preparation and material adoption. Neither browser branch starts `Task.Run` or a worker. The desktop worker path and its existing debounce remain available. One source preparation is an indivisible job step; the scheduler's elapsed-time budget cannot preempt that CPU work. Explicit `PrepareUberVariantImmediately` remains a synchronous preparation API for callers that intentionally require immediate state.

Every queued caller preparation captures a request serial, cancellation token, authored-state revision, and shader-state revision. Checks bracket the request status callback, preparation, requested-state publication, status callbacks, and shader adoption. A later request or explicit immediate preparation invalidates older caller work. Material teardown sets its teardown flag before owned shader destruction; delayed and queued jobs check that flag and cannot adopt after disposal. A failed caller preparation records the underlying reason and preserves the current authored shader and active variant rather than restoring a canonical shader. If a callback supersedes adoption, the caller path restores only state still owned by that attempted adoption.

The delayed path also captures the caller `JobManager` before returning to its host. Scheduler shutdown before delay expiration or while work is queued cannot cause the continuation to create an implicit worker scheduler. Terminal scheduling failures and job cancellation publish an immutable, request-tagged receipt; they do not invoke material property callbacks from a timer or arbitrary continuation. The material's owner consumes that receipt during variant readiness or pipeline-source preparation, records the original reason as a failed status, and can retry with a fresh request after a caller scheduler is configured. A newer request and teardown discard older receipts. Edit-debounce scheduling uses the same rule.

Generated-source cache path normalization and canonical rehydration only probe host files when `ShaderSourceResolver.CanAccessHostShaderFiles` admits those reads. Registered source snippets can still resolve when published by the host; generated GLSL is not a WGSL compiler or a replacement for an exact cooked artifact. An unavailable canonical browser shader reports `UberVariant.CanonicalSourceUnavailable` when rehydration cannot use the published shader catalog. A generated variant still needs the exact cooked WebGPU program contract. The current `WebGpuMaterial.Generate` semantic catalog admits declared engine material variants, while the Uber GLSL path has no general runtime GLSL-to-WGSL conversion. Its generic program path reports `WebGPU.Program.ArtifactMissing` if the exact companion is absent; a named Uber hash/descriptor error remains useful for the broader cooked-contract admission work. No rendered Uber acceptance is claimed here.

Narrow `XREngine.Runtime.Rendering` Release build with the pinned build helper passed with zero warnings and errors. An isolated build of the reviewed source tree with only the two Uber source overlays and the one pipeline-readiness hunk also passed with zero warnings and errors, using its own output directory while unrelated shared-tree editing continued. The focused caller-scheduler runtime probe under ignored validation scratch passed delayed request, pump ownership, supersession, debounce, disposal, preparation failure, and reentrant adoption checks. It also passed scheduler rejection before delay expiration, queued-job cancellation without canceling the request token, owner-side failure observation, status-callback failure, fresh-scheduler recovery, supersession of an unobserved old failure, and pipeline-source gate observation. A stopped desktop caller manager rejects an off-owner delayed submission with its original caller-thread error; the receipt reports `UberVariant.CallerJobUnavailable` with that detail. The separate broad Browser build and physical browser page/pixel evidence are outside this bounded source change.

The [caller blocking inventory](../platform/browser-caller-blocking-inventory-2026-10-03.md) should move authored Uber async rebuild from the unbounded worker-call classification to this caller-job boundary, while retaining its broader browser cooked-program and immediate-preparation limitations. The inventory's lexical `Task.Run` count will still include the desktop branch.
